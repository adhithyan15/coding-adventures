## Summary

Phase 8a (full-coverage queue) extends Ruby compound-assignment support beyond the pre-existing `+= -= *= /= ||= &&=` to cover **six more operators**: `%= **= <<= &= |= ^=`.  Combined, the parser now accepts Ruby's complete compound-assign family on local variables, minus `>>=` (explicitly deferred — see below).

## Lexer

`fuse_compound_assigns` widens its left-flank recognition: in addition to the existing `Plus`/`Minus`/`Star`/`Slash` typed tokens and `Name("||")` / `Name("&&")`, it now also recognises `Name("%")`, `Name("**")`, `Name("<<")`, `Name("&")`, `Name("|")`, `Name("^")`.  Same adjacency gate (no whitespace before `=`), same fold target (`Name("%=")`, etc.).

## Grammar

```ebnf
assignment = NAME ( EQUALS | "+=" | "-=" | "*=" | "/="
                  | "%=" | "**=" | "<<=" | "&=" | "|=" | "^="
                  | "||=" | "&&=" ) expression ;
```

`_grammar.rs` regenerated via `grammar-tools compile-grammar`.

## Lowering

`lower_assignment` learns six more cases in its compound-op dispatch.  Every form desugars to the same `Stmt::Assign` + `BuiltinCall(op, [VarRef(x), rhs])` shape that `+= -= *= /=` already uses, and triggers `Feature::MutableBindings`:

| Source     | SIR shape                                                       |
|------------|-----------------------------------------------------------------|
| `x %= y`   | `Assign(x, BuiltinCall("%",  [VarRef(x, Local), <y>]))`         |
| `x **= y`  | `Assign(x, BuiltinCall("**", [VarRef(x, Local), <y>]))`         |
| `x <<= y`  | `Assign(x, BuiltinCall("<<", [VarRef(x, Local), <y>]))`         |
| `x &= y`   | `Assign(x, BuiltinCall("&",  [VarRef(x, Local), <y>]))`         |
| `x \|= y`  | `Assign(x, BuiltinCall("\|", [VarRef(x, Local), <y>]))`         |
| `x ^= y`   | `Assign(x, BuiltinCall("^",  [VarRef(x, Local), <y>]))`         |

Same builtin-naming convention as the pre-existing family: BuiltinCall name = surface operator string.

## v0 deferred limitation

- **`>>=` is NOT yet supported**.  The 1.8-baseline lexer state machine splits `>>` into two separate `>` tokens; folding requires a dedicated `>>` pre-fusion pass.  Both the parser and lower paths are designed to accept `>>=` cleanly once `>>` becomes a single `Name(">>")` token, so the follow-up will be a small lexer-only change.
