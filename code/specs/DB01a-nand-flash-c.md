# DB01a — C Profile for Logical SLC NAND Flash

This document pins the C17 profile of [DB01](DB01-nand-flash.md). It does not
change the language-neutral model or the shared JSON trace format. The package
is `code/packages/c/nand-flash`; public declarations live in
`include/nand_flash.h`.

## Public interface

The API uses an opaque `NandFlash` handle, `size_t` indices and lengths,
`uint8_t` bytes, a `uint64_t` erase count, and a `bool` for whether an erase
ceiling is present. `nand_flash_create` accepts dimensions and
`has_max_erase_cycles` plus `max_erase_cycles`, and writes a new handle only on
success. When the flag is false the numeric maximum is ignored. A null output
handle pointer is an invalid-argument refusal. Pass a writable output slot
that does not own a live handle. Creation sets that slot to null before
geometry validation, so failed creation leaves no handle in it.
`nand_flash_destroy(NULL)` is a no-op.

The API exposes read-only geometry getters, `nand_flash_read`,
`nand_flash_program`, `nand_flash_erase_block`, per-block erase-count query,
and per-page programmed-marker query. Read copies exactly one page into a
caller-owned destination. Program copies exactly one page from a caller-owned
source. The device retains no caller pointers; buffers may be reused or changed
after calls return. Read/program buffers must be non-null. Input and output
buffers must not overlap live storage owned by the opaque handle; the handle's
representation is not exposed. The source is copied only after payload pointer
and fixed byte count validity are established. A read destination may not be
modified on any refusal.

Geometry getters return zero for a null handle; valid dimensions are positive,
so zero is an unambiguous null sentinel.

Fallible functions return `NandFlashStatus`. The enum distinguishes success,
invalid API argument, invalid geometry, invalid block, invalid page, invalid
payload pointer, wrong payload length, already-programmed page, exhausted erase
limit, and allocation failure. `nand_flash_status_message` maps statuses to
stable DB01 error messages; API argument errors and allocation failure use
`invalid API argument` and `allocation failed`, respectively. Status names and
messages for DB01 domain errors match DB01 exactly. A null handle on an
operation returns invalid API argument.

## Representation and bounds

The implementation is dependency-free ISO C17 on targets with `uint8_t`,
`uint64_t`, and a `size_t` large enough to represent 16 MiB. The accepted geometry is
exactly DB01's ranges: blocks 1..1024, pages per block 1..256, page bytes
1..65536, and total storage at most 16 MiB. Maximum erase cycles are either
absent or in 0..9007199254740991. The C API's dimensions use `size_t`; range
checks happen before multiplication or allocation. Products are checked against
the DB01 cap and against `SIZE_MAX`. Pages, programmed markers, and erase
counters are separately allocated or packed with checked byte arithmetic.
New pages contain `0xFF`, counters are zero, and markers are clear.

## Validation precedence and atomicity

Construction validates the output argument, geometry ranges, checked product,
then allocation. For media commands, reject a null handle first, then check
block before page. Read and program check the buffer pointer then exact length.
Program checks both before the programmed marker. A null buffer with a valid
address is an invalid payload pointer. Erase checks block before erase budget.
Query output slots are writable and must be non-null. A query validates its
handle, output slot and any address before writing the output.
No failed command mutates device state. Reads do not mutate state and only copy
after all validation succeeds. Erase prepares all derived offsets before
mutation and then resets the complete block, clears all its markers, and
increments its counter once.

Because the API receives a fixed `size_t data_length`, it can distinguish a
null payload from a non-null payload with the wrong size but cannot determine
whether an arbitrary non-null C pointer actually addresses that many readable
bytes. Such caller memory validity is a precondition. Similarly, overlapping
caller buffers are supported unless the buffer aliases opaque device storage,
which cannot be obtained through this API.

## Conformance and evidence

The canonical `code/specs/fixtures/database-media-v1/nand-flash.json` remains
the shared trace input. A test-only fixture adapter decodes the bounded JSON;
the runtime library has no JSON dependency. The native trace runner compares each operation
result, typed status/message, returned bytes and full state after every step.
No expected state is generated by the C implementation itself.

Tests additionally cover limits and one-past-limit dimensions, safe arithmetic,
null and wrong-size buffers, all refusal-order collisions, read-copy
independence, caller-buffer mutation after program, erase atomicity, seeded
operation sequences against a separate byte-array model, malformed/fuzzed
command streams, and exhaustive short histories on a small device. Sanitizers
are run where compiler support exists. These tests are evidence for this
implementation; they are not a formal proof of arbitrary C memory safety or
all possible histories.

The package supplies POSIX and Windows build entries using the repository's
native C harness where available, a README with ownership and usage guidance,
and a changelog. DB-E05 gives the package an exact dependency on the NAND
fixture for selection, hashing, and the exported build graph. The native
test runner reads that same canonical trace. [Fixture routing](DB-E01-media-fixture-routing.md)
