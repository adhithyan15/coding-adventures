## Unreleased — LANG84 phase 6e: JavaScript on every backend

- `Language::JavaScript` (`--lang javascript` / `js`, `.js`) reaches `javascript-iir-compiler`'s release path: `--lang javascript@<edition>` compiles against exactly one claiming ECMAScript edition (es2016 … es2025, default es2020), recorded in `IIRModule::release`; `es20` is `UnknownRelease` and `es5`/`es2015` are `ReleaseNotAvailable`, never a fallback. `has_release_inventory` covers JavaScript, and `release_inventory.py`'s `MATRIX_LANGUAGES` already mapped it to `ecmascript`.
- The module is LANG83 registry ops only, so no backend has JavaScript code: `+ - * /` and unary `-` are the PR6c IEEE ops `f64_*`, `console.log` is `write_f64_js` with `putchar` for the spaces, the newline and the `-` of `-0` (behind an `f64_signbit`/`cmp_gt` test), and a ReferenceError is `trap "Trap.ReferenceError"` (new built-in kind, stable id 7).
- 38 `lang_matrix` rows run the `es-number-log` corpus verbatim (new `js_case!` macro) on es2016 and es2021, the two IIR-identity class representatives, and on the default es2020. The 11 literal-only rows declare `EVERY_COLUMN`; the 27 with arithmetic declare the new `IEEE_COLUMNS` (all but BEAM, which refuses `f64_*` at compile time with `UnsupportedOps`, as stage B allows). JavaScript is 38 rows / 277 cells (`feature_coverage_doc_counts_match_programs_source`, LANG-VM-FEATURE-COVERAGE.md).
- New tests: `javascript_rows_run_on_every_available_backend`, `javascript_rows_agree_with_the_host_node_oracle` (node v22), `javascript_rows_pass_the_lang83_check_on_all_nine_backends` (also emits every row's CLR IL, lowers every literal-only row to BEAM bytes and pins that BEAM refuses exactly the arithmetic rows, naming only `f64_*`), `javascript_rows_compile_and_run_on_the_jit_without_its_interpreter_fallback` (compiles `main` to JIT bytecode and runs it compiled; the matrix's JIT cells go through `execute_with_jit`, which interprets printing functions), `javascript_reference_errors_trap_after_output_on_every_available_backend` (undeclared and TDZ reads, `StdoutThenTrap("1", "Trap.ReferenceError")`, all eight columns) and `javascript_rows_run_their_corpus_case`; the lib test `javascript_language_parses_detects_and_selects_editions`.
- `run_vm` and `run_jit` (both tiers) register `write_f64_js` into the one ordered output buffer, through vm-core's `float_format`.
- `releases.csv` claims `backend_status` `es-number-log` for es2016–es2025; `release_inventory.py check --matrix` reports 10 claims with 38 cells direct and 92 by IIR class.
- Local runs (no `dotnet`, no `erl`): the JavaScript rows ran 228 cells on native x86-64, LLVM, WASM, JVM, VM and JIT and skipped the 49 CLR/BEAM cells; all 38 rows agree with host node v22.22.0.
- `op_conformance`: a case is "lowered" on BEAM only if BEAM can also hold its constants. The PR6a float-table cases print `inf`/`nan` constants, so iir-to-beam's new non-finite-constant refusal makes BEAM refuse them at compile time. Before that refusal, BEAM compiled them into modules no Erlang loader could read. A new test, `beam_refuses_non_finite_float_constants`, pins the refusal, and also checks that a finite table still compiles.
- JavaScript's `main` returns an `i64` exit status, `const 0` then `ret`, instead of `ret_void`. The BEAM launcher prints `main()`'s result and parses it as an integer, and a void `main` printed `[]`. Every JavaScript BEAM cell failed in CI because of this, even when stdout was correct.
