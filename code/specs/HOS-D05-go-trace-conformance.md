# HOS-D05-GO3 — Captured Go RV32I pipeline conformance case

## Goal

Capture a fresh, small RV32I program and the actual per-cycle trace produced by
the published Go classic five-stage `core.Core`. The capture is local evidence
for this Go pipeline after typed forwarding and load-use placement fixes. It is
not a copy or reconstruction of the unavailable older HOS09a fixture and does
not claim parity with another language or simulator.

## Input contract

The versioned JSON input contains little-endian guest bytes, RAM size, initial
word values, and a positive maximum cycle count. The bounded guest exercises
both operand bypasses in separate situations: simultaneous distinct EX/MEM
sources feeding a store, and a load-use dependency held in ID until the loaded
value forwards from MEM into a taken branch. The branch skips a wrong-path
register write and reaches a bounded terminal ECALL. Only aligned, in-range
flat-RAM accesses are used.

The test loads the input fixture, constructs the real five-stage Go core, and
also runs the same bytes and initial memory through the separate sequential
`RiscVSimulator`. Fixture input drives execution; expected trace data is only
used for comparison after execution.

## Captured output contract

The expected JSON is captured from the actual Go core, not generated by the
sequential oracle. It records the cycle number, F/D/E/M/W occupancy by PC and
mnemonic, typed EX operand forwards, stall and flush flags, ordered retired
PCs, aggregate stall/flush/forward counts, final registers, and final RAM
words. The test compares this projection with a fresh run and independently
checks the staged machine's final registers, complete RAM image, and retired
PC path against the sequential simulator.

The fixture has its own SHA-256 content identity. Changing instructions,
initial memory, trace projection, or expected output requires recapturing from
the actual Go pipeline and recording the new digest. The trace is evidence of
the implementation's current deterministic behavior, not an architecture-wide
golden.

## Explicit limits

The program has one current-process teaching path ending at ECALL. Stores take
effect in MEM before WB, so the capture does not establish precise store
retirement or rollback. It has no faulting access, MMIO, traps to a handler,
interrupts, OS boot, multi-cycle memory latency, or non-classic pipeline
profile. The final RAM comparison is for aligned in-range word accesses only.

## Acceptance checks

- Replay the JSON input on the actual classic five-stage Go pipeline and match
  the committed cycle projection exactly.
- Assert separate operand tags/values, one load-use stall, taken redirect,
  wrong-path suppression, and the captured terminal path.
- Compare staged and sequential retired instruction PCs, all 32 registers,
  and all words of the bounded flat RAM image.
- Keep the case test-only and package-local; do not add a shared fixture
  registry or alter unrelated language consumers in this slice.
