# CI installs `cargo-tarpaulin` UNPINNED (`cargo install cargo-tarpaulin`), so coverage can break with no repo change

`chief-of-staff-biometric-approval` built and passed on ubuntu-latest with the ptrace engine on 2026-08-14 (PR #11506) and SIGILLed months later on untouched code — the tool moved, not the crate. Diff-based CI hides this: a package is only rebuilt when it changes, so a tool-drift breakage sits dormant until some unrelated PR triggers a near-full rebuild, and then looks like *that* PR's fault. When a package fails on code nobody edited, check the tool version before the diff. Same family as the existing "don't pin tool versions to `latest`" lesson. **Fixed 2026-09-02**: `ci.yml` now installs `cargo-tarpaulin --version 0.37.2 --locked`. **Pin to the version that FIXES the bug you are citing, not the one you happen to have installed.** The first attempt pinned 0.35.2 -- the version on my machine -- which is the last release *before* upstream fixed this very SIGILL in 0.35.3 (yanked, republished as 0.35.4). That would have frozen CI on the bug the pin was written to prevent, across the 17 of 20 invocations that use the default ptrace engine. Check the upstream changelog for the fix version before pinning. `--locked` is not optional here -- without it Cargo re-resolves tarpaulin's own dependency tree on every run, so a patch release in any transitive dep reintroduces exactly the drift the version pin removes. And `--locked` WITHOUT `--version` is not a pin at all -- it locks the deps of whatever version happens to resolve. `cargo install --locked cargo-geiger` in `lang-runtime-safety.yml` looks pinned and is not.
