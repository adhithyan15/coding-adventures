# UI24 — mosaic-emit-dispatch: Flux Event Dispatch Pattern

**Status:** Specification (draft)
**Layer:** UI / backend emitter
**Depends on:** UI13 (mosmodel), UI20 (mosaic-emit-react), UI23 (mosaic-pipeline)
**Supersedes:** the per-callback prop pattern documented in UI20 §6

---

## 1. Purpose

In every Mosaic backend that targets a reactive UI framework (React, SwiftUI,
Compose, etc.), the `emit` declarations of a mosmodel component are the
component's *outbound* event channels. The original Mosaic React backend
(UI20) lowered each `emit` to an individual optional callback prop:

```tsx
// CURRENT (UI20)
interface GridProps {
  columnHeaders: string[];
  ...
  onNavigate?:   (row: number, col: number) => void;
  onEditCommit?: (value: string) => void;
  onEditCancel?: () => void;
}
```

This works for components with one or two emits, but it does not scale to
spreadsheet-class components with six or eight events. The host application
ends up threading six or eight closures through every level of its tree, each
of which it constructs by calling `useCallback` to avoid re-rendering the
component on every parent render. The mental model also diverges from the
modern React idiom of routing all events through a single `useReducer`
dispatcher.

UI24 replaces the N-callback pattern with a **single discriminated union of
events** and a **single `dispatch` prop**:

```tsx
// TARGET (UI24)
type GridEvent =
  | { type: "navigate";   row: number; col: number }
  | { type: "editCommit"; value: string }
  | { type: "editCancel" };

interface GridProps {
  columnHeaders: string[];
  ...
  dispatch: (event: GridEvent) => void;
}
```

This is the Flux / Redux / `useReducer` pattern, which TypeScript exhausts
correctly through discriminated-union narrowing in switch statements.

### Why this is better

| Concern | N callbacks | Single dispatch union |
|---|---|---|
| Props the host passes | N (one per emit) | 1 (`dispatch`) |
| `useCallback` memoization needed | Yes, N times | No (dispatch is stable) |
| Pairs with `useReducer` naturally | No (must wrap each callback) | Yes (literally `dispatch` from `useReducer`) |
| Exhaustive-switch checking | No | Yes |
| Recording / replaying events | Hard (closures) | Trivial (events are plain data) |

### Scope

This spec covers the **emit lowering** for all current and planned Mosaic
backends. It does **not** modify the mosmodel `.mil` grammar — the source-side
emit declaration syntax from UI13 is unchanged.

## 3. React backend — generated output format

### 3.1 The event union type

For every component, the React emitter generates one TypeScript discriminated
union named `<ComponentName>Event`:

```tsx
type GridEvent =
  | { type: "navigate";   row: number; col: number }
  | { type: "editStart";  row: number; col: number }
  | { type: "editCommit"; value: string }
  | { type: "editCancel" }
  | { type: "scroll";     offset: number }
  | { type: "select";     startRow: number; startCol: number;
                          endRow:   number; endCol:   number };
```

Each `emit` declaration becomes one variant of the union:

- The `type` field is a string literal — see §5 for the conversion rule.
- Each emit parameter becomes one camelCase field of the variant.
- Void emits (no parameters) produce a variant with only the `type` field.

### 3.2 The props interface

The component props interface receives **one** new field, always required,
named `dispatch`:

```tsx
interface GridProps {
  columnHeaders: string[];
  columnWidths:  number[];
  ...
  dispatch: (event: GridEvent) => void;
}
```

`dispatch` is **never** optional, even for zero-emit components (see §6). This
gives the host application a uniform contract: every Mosaic component takes a
`dispatch` prop, full stop.

### 3.3 The complete generated file

For a Mosaic Grid component, the React backend now emits:

```tsx
// Auto-generated by mosaic-emit-react. Do not edit.
import React from "react";

type GridEvent =
  | { type: "navigate";   row: number; col: number }
  | { type: "editStart";  row: number; col: number }
  | { type: "editCommit"; value: string }
  | { type: "editCancel" }
  | { type: "scroll";     offset: number }
  | { type: "select";     startRow: number; startCol: number;
                          endRow:   number; endCol:   number };

interface GridProps {
  columnHeaders:  string[];
  columnWidths:   number[];
  viewportRows:   Array<string[]>;
  totalRows:      number;
  viewportOffset: number;
  selectedRow:    number;
  selectedCol:    number;
  editRow:        number;
  editCol:        number;
  editContent:    string;
  dispatch:       (event: GridEvent) => void;
}

export function Grid({
  columnHeaders,
  columnWidths,
  viewportRows,
  totalRows,
  viewportOffset,
  selectedRow,
  selectedCol,
  editRow,
  editCol,
  editContent,
  dispatch,
}: GridProps) {
  return (
    <table>
      {/* JSX that closes over `dispatch` to fire events */}
    </table>
  );
}
```

Structural invariants:

1. `import React from "react"` is the first non-comment line.
2. The event union `type` declaration comes immediately after the import.
3. The props interface comes after the union.
4. The function declaration comes last.
5. `dispatch` is always the **last** field of the destructuring pattern and
   the last property of the interface. This makes the prop trivial to spot in
   diffs and code reviews.

## 4. Backend mapping table

Every Mosaic backend implements the dispatch contract idiomatically for its
target. The wire format differs; the semantics are identical: *one channel
out, payloads tagged by emit name.*

| Backend | Mechanism | Notes |
|---|---|---|
| **React (TSX)** | `type XEvent = \| { type: "..." } \| ...`; `dispatch: (e: XEvent) => void` prop | Idiomatic Flux / `useReducer` pattern. |
| **WebComponent (JS)** | `this.dispatchEvent(new CustomEvent(type, { detail: payload, bubbles: true, composed: true }))` | Single DOM event per emit. Host listens with `addEventListener(type, …)`. |
| **HTML (static)** | No-op | Static HTML has no runtime — emits are not rendered. The HTML backend ignores the emits list entirely. |
| **paint-vm** | Stored per-emit callback closure in the renderer state; called when the corresponding widget fires | Already closure-based — keep the existing shape. A future `paint-vm-dispatch` adapter may unify this, but it is out of scope for UI24. |
| **Qt (future)** | One `Q_SIGNAL` per emit: `void navigated(double row, double col);` | Qt's native signal/slot system already provides the dispatch surface — no need to invent a union. |
| **SwiftUI (future)** | `enum XEvent { case navigate(row: Double, col: Double); ... }` + `var dispatch: (XEvent) -> Void` | Same pattern as React with Swift enums. |
| **Jetpack Compose (future)** | `sealed class XEvent { data class Navigate(...) : XEvent() }` + `onEvent: (XEvent) -> Unit` | Same pattern as React with Kotlin sealed classes. |
| **XAML / WinUI3 (future)** | One .NET event per emit: `event EventHandler<NavigateEventArgs> Navigated;` | Idiomatic for the platform; consumers wire with `+=`. |
| **Win32 / GDI (future)** | One C function pointer per emit, stored in a callbacks struct | Idiomatic for the platform; no language-level event system. |

The choice between "single union" and "N native events" per backend follows
the principle: **use the host language's idiom**. React/SwiftUI/Compose
benefit from union dispatching because they pair with reducer-style state.
Qt/.NET/Win32 have first-class event systems already, so the spec maps each
emit to one event there.

## 5. Emit name → union `type` field conversion

The conversion from a mosmodel emit identifier (kebab-case or `onCamelCase`)
to the React union's `type` literal follows three steps:

1. **Strip a leading `on` prefix**, case-insensitively. The leading `on` is a
   common convention in mosmodel for naming output channels — it would be
   noise in a union variant where `type` already says "this is an event."
2. **Convert the remainder to camelCase**.
3. The result is the string literal used as the `type` field value.

### Conversion table

| Mosmodel emit name | React `type` field |
|---|---|
| `onClick` | `"click"` |
| `onNavigate` | `"navigate"` |
| `onEditStart` | `"editStart"` |
| `onEditCommit` | `"editCommit"` |
| `onEditCancel` | `"editCancel"` |
| `onScroll` | `"scroll"` |
| `onSelect` | `"select"` |
| `onLongPress` | `"longPress"` |
| `onFormulaChange` | `"formulaChange"` |
| `dispatch` | *(reserved — see §5.1)* |

### 5.1 Reserved names

The names `dispatch`, `children`, and `key` are **reserved** as union `type`
values because they collide with React conventions or the dispatch prop
itself. If an emit lowers to one of these reserved names, the emitter must
fail with a clear error:

```
mosaic-emit-react: emit 'dispatch' collides with reserved React prop name
  in component Grid (Grid.mil:14)
  use a different emit name such as 'onDispatch' or 'request'
```

## 6. Zero-emit components

A component with no emit declarations still receives a `dispatch` prop, with
the union type being the empty union `never`:

```tsx
type ButtonEvent = never;

interface ButtonProps {
  label: string;
  icon:  string;
  dispatch: (event: ButtonEvent) => void;
}

export function Button({ label, icon, dispatch }: ButtonProps) {
  ...
}
```

### Why `never`?

- The function `(event: never) => void` is callable from any code path, but
  no code path can construct a value to pass to it. TypeScript flags any
  attempt to call it with a real argument.
- This preserves the uniform contract: every Mosaic component takes a
  `dispatch` prop. Host code does not need conditional logic ("does this
  component have a dispatch?") and HOC wrappers can spread props freely.
- The cost is one extra prop on zero-emit components — typically a `<Button>`
  pure-decoration component. The cost is negligible; the consistency is
  worth it.

## 7. Host application usage pattern

The intended host-side usage is `useReducer`:

```tsx
import React, { useReducer } from "react";
import { Grid, GridEvent } from "./components/Grid";

interface AppState {
  selectedRow: number;
  selectedCol: number;
  // ... rest of the application state ...
}

// The reducer action type unions every component's event type
// with any host-internal actions.
type AppAction =
  | GridEvent
  | { type: "loadData"; data: string[][] };

function reducer(state: AppState, action: AppAction): AppState {
  switch (action.type) {
    case "navigate":
      return { ...state, selectedRow: action.row, selectedCol: action.col };
    case "editCommit":
      // ... commit logic ...
      return state;
    case "editCancel":
      return { ...state, editRow: -1, editCol: -1 };
    case "scroll":
      return { ...state, viewportOffset: action.offset };
    case "loadData":
      // ... load logic ...
      return state;
    // TypeScript will error if any case is missing because of exhaustive
    // discrimination on the `type` literal.
  }
}

export function App() {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <Grid
      columnHeaders={state.columnHeaders}
      columnWidths={state.columnWidths}
      ...
      dispatch={dispatch}
    />
  );
}
```

Key observations:

- The host passes the *literal* `dispatch` from `useReducer` directly to the
  component. No closure wrapping, no `useCallback`.
- The host's reducer action type is a union of every Mosaic component's event
  type plus host-internal actions. Adding a new event from a Mosaic component
  is automatic.
- Discriminated narrowing on `action.type` makes each case statement strongly
  typed. TypeScript catches missing cases at compile time.

## 8. Security

The string literal used as the `type` field of each union variant is derived
at compile time from the emit identifier in the `.mil` source. The mosmodel
grammar already restricts emit names to `KEBAB_IDENT` (UI13 §4), which is
`[a-z][a-z0-9]*(-[a-z][a-z0-9]*)*`. The `on`-prefix handling in §5 is also
purely lexical. The set of characters that can ever appear in a `type`
literal is therefore restricted to `[a-zA-Z0-9]`. No characters that would
escape a TSX string literal (`"`, `\`, `<`, `>`, `{`, `}`) can appear.

The React backend's existing `is_safe_js_identifier()` check (UI20 §3.3) also
guards against bad identifiers landing in destructuring patterns. UI24 adds
no new injection surface.

## 9. Migration from the UI20 N-callback pattern

The change is **backend-only**. No `.mil`, `.mll`, or `.msl` source files
require any modification. Host applications that consumed the old N-callback
output must change:

| Before (UI20) | After (UI24) |
|---|---|
| `<Grid onNavigate={(row, col) => …} onEditCommit={v => …} />` | `<Grid dispatch={dispatch} />` |
| `onNavigate` is optional | `dispatch` is always required |
| Host has N closures | Host has one `useReducer` |

The React emitter's CHANGELOG should call this out as a breaking change.
Until a host has migrated to the dispatch pattern, it can simply build a
local shim:

```tsx
function dispatchFromCallbacks(callbacks: {
  onNavigate?: (row: number, col: number) => void;
  onEditCommit?: (value: string) => void;
  /* … */
}): (event: GridEvent) => void {
  return event => {
    switch (event.type) {
      case "navigate":   callbacks.onNavigate?.(event.row, event.col); break;
      case "editCommit": callbacks.onEditCommit?.(event.value);        break;
      /* … */
    }
  };
}
```

This shim is **not** part of UI24 — it is a documentation aid for projects
mid-migration.

## 11. Out of scope for UI24

- **WebComponent / paint / Qt emitter changes** — UI24 specifies how those
  backends *map* the dispatch concept, but their implementation lives in
  their own emitter crates and is tracked separately.
- **Connecting JSX click handlers to `dispatch` calls** — UI24 only fixes the
  *interface shape*. Wiring `<td onClick>` to `dispatch({ type: "navigate", … })`
  for Grid-class primitives is the job of the moslayout `connects` clause
  (UI14 §6) and the React emitter's primitive handlers.
- **A union type discriminator other than `"type"`** — Some Redux-style codebases
  prefer `"kind"` or `"$"`. The choice is fixed at `"type"` in UI24 to align
  with the most common React + TypeScript practice (Redux Toolkit, useReducer
  examples in the React docs).
- **Reducer code generation in the emitter** — The emitter generates the
  *event union*, not the reducer. The reducer is host-application logic.

## 12. Relationship to other specs

- **UI13 mosmodel** — emit declaration syntax (unchanged).
- **UI14 moslayout** — `connects` clauses fire emits in response to native
  events (unchanged).
- **UI20 mosaic-emit-react** — the prior, per-callback prop pattern. UI24
  supersedes §6 (and any related section) of UI20. Re-read UI20 §1–§5, §7–§10
  for everything else (slot lowering, type mapping, JSX framing, etc.) that
  UI24 leaves untouched.
- **UI23 mosaic-pipeline** — pipeline-level versioning. A component whose
  React backend output changes from "N callbacks" to "dispatch union" is a
  **breaking change** to the generated TypeScript API — bump the component's
  *minor* version (e.g., `version 1.0` → `version 2.0`) because the
  TypeScript prop surface is part of the published interface contract.
