# HL27 — Sharded Script Ductus ownership

**Status:** specification, 2026-08-27

**Extends:** HL24's executable-evidence ownership rule and HL25's shard-native
script inventories. Tracks #13298 and the parent contention program #13193.

## 1. Outcome

Independent writing-system authors can add or correct ductus data, geometry
evidence, and filmstrip evidence without editing any of these former shared
authoring surfaces:

```text
src/strokes.ts
tests/strokes.test.ts
tests/ductusview.test.ts
```

Runtime consumers retain the existing `DUCTUS`, `ductusKey`, helper, and type
exports. The migration changes ownership and module boundaries, not glyph data,
stroke order, source provenance, rendering, or validation strength.

## 2. Source ownership

`src/strokes.ts` becomes a compatibility entry point. It owns the public types,
geometry helpers, and deterministic assembly of the registry, but no authored
glyph paths. Authored paths live under:

```text
src/strokes/japanese.ts
src/strokes/chinese.ts
src/strokes/devanagari.ts
src/strokes/cyrillic.ts
src/strokes/gujarati.ts
src/strokes/hebrew.ts
src/strokes/arabic-family.ts
src/strokes/kannada.ts
src/strokes/telugu.ts
src/strokes/malayalam.ts
src/strokes/tamil.ts
```

The Arabic-family module is one deliberate exception to one-module-per-script.
The existing data shares checked stroke arrays among Arabic, Perso-Arabic, and
Urdu-Nastaliq while retaining separate provenance. Splitting those records
would either introduce cross-owner mutation/import cycles or duplicate shared
geometry and let the copies drift. That semantic coupling belongs together.

Every owner module exports an ordered sequence of `[key, LetterDuctus]` entries.
The compatibility entry point imports the fixed list above and inserts each
entry into one ordinary object in the pre-migration order. It must not use
filesystem APIs, dynamic runtime discovery, or a hand-maintained per-glyph
registry. Adding a glyph edits only its owner module.

The fixed owner list is a bounded browser-build boundary: eleven imports for
the eleven existing ownership domains. A new writing system may add one owner
import; an ordinary glyph may not.

## 3. Identity and ordering

The migration preserves all observable registry behavior:

1. every pre-migration own key exists exactly once after assembly;
2. `Object.keys(DUCTUS)` has the same order;
3. every key has the same parsed data;
4. legacy unscoped keys remain own properties with their existing script and
   glyph identities;
5. scoped keys remain collision-safe through `ductusKey(script, glyph)`;
6. intentionally shared stroke-array and stroke-object identities in the
   Arabic family remain shared; and
7. `DUCTUS` remains an ordinary object while lookups continue to use own-key
   checks before accepting a value.

An owner sequence must reject a duplicate key locally. The aggregator must
also reject a duplicate across owners instead of silently allowing the later
owner to overwrite the earlier one.

## 4. Executable evidence ownership

Exact script claims move along the same seam as the source they prove:

```text
tests/strokes/<owner>.test.ts
tests/ductusview/<owner>.test.ts
```

The two former monoliths retain only genuinely common behavior. Examples are
polyline truncation, join-gap measurement, hostile object-key lookup, generic
registry completeness, generic font-ink/coverage measurement, and renderer
behavior that is independent of a particular writing system.

Common expensive setup belongs in test helpers, not in copied owner suites.
Owner tests may import those helpers, but one owner may not register assertions
through a central assertion list. Vitest discovers the `*.test.ts` modules, so
adding evidence never edits an aggregator.

Moving tests is structural. Every pre-migration assertion survives with the
same matcher and data. A test may be generalized only in a separately reviewed
change after the migration proves parity.

## 5. Migration proof

Before deleting authored data from the monolith, record and verify:

- the exact ordered key list and its SHA-256;
- a deterministic serialization hash of all registry data;
- the key count and counts grouped by canonical `script`;
- the exact Vitest assertion count for the package;
- the identity-sharing relationships used by Arabic-family derived entries;
  and
- the complete source-to-owner assignment, with no entry left in the
  compatibility module and no entry present in two owners.

The implementation should be generated by an AST-aware or syntax-checked
mechanical split. After generation, run the narrow TypeScript/Vitest parser
immediately; statement or test-count parity does not prove generated source is
syntactically valid.

## 6. Anti-regression gate

A source-shape test keeps the compatibility entry point bounded:

- no `LetterDuctus` object literal or `ductusKey(...): {` authored entry may
  return to `src/strokes.ts`;
- every fixed owner module participates once;
- owner modules do not import another owner except the documented
  Arabic-family sharing that remains internal to that one module; and
- the two root test files contain no script-named or glyph-specific claims.

The gate measures structure, not a fragile line-count ceiling. Formatting or
documentation growth in a legitimate shared helper must not fail it.

## 7. Acceptance

Completion requires all of the following:

1. an unrelated glyph change touches one owner source module and, when needed,
   its matching owner evidence modules only;
2. registry key order, serialized data, source citations, shared identities,
   and assertion coverage match the pre-migration pins;
3. duplicate local and cross-owner keys fail closed;
4. the public Script Ductus API and Language Ladder behavior are unchanged;
5. the full Script Ductus, Human Language Data, and Language Ladder suites pass;
6. the affected-package build passes;
7. the compatibility and root evidence anti-regression gates pass; and
8. an independent security/data-integrity review reports no unresolved issue
   before push.
