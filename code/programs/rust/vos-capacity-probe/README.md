# vos-capacity-probe

The **solver and enumeration capacity probe** of the verified-OS program (VOS-028b,
[VOS30](../../../specs/VOS30-proof-route-and-capacity.md) section 9). Class P: a program, not a
library; no other crate depends on it.

## The question it answers

VOS00 promised a third proof stage: symbolic execution of each compiled kernel entry, mitered
against the model and DRAT-checked (bar X3). Whether that is buildable depends on how big an
obligation the repository's own `cdcl-sat`, `bit-blaster` and `drat-check` can swallow. The advisor
measured it once, in a scratch crate, with the checker's limits raised. This tool measures it
again, **reproducibly**, with the shipped limits, and ends by stating the VOS30 section 8.3
decision from the numbers.

```text
  experiment   what it sizes
  -----------  ------------------------------------------------------------------------------
  A1, A2       the bitmap shapes: `pick` (clz against a priority chain), insert and remove
  B1 .. B4     straight-line RV32I with synthetic divergence: the identical-sequence collapse
               (B1), the monolithic miter (B2, the cliff), the same with cut points (B3, the
               number that funds VOS-029), arithmetic with no cut point (B4)
  C1, C2       self-composition (constant time): two copies, public shared, secret fresh
  D1 .. D4     memory with no array theory: an eq/ite chain against a mux tree (D1), concrete
               offsets (D2), case-split on the index (D3), cut points between accesses (D4)
  E1, E2       enumeration: the generated by-value harness's throughput and refusals
```

## What it found (VOS30 section 8.5)

The committed results (1,625 rows, `code/specs/data/vos30-capacity-results.json`) give the
section 8.3 outcome **row 1, Infeasible: re-plan X3**, provisional until a named reviewer
regenerates the full tier. Certified per-instruction cuts, `pick` and the bitmap shapes are green
with a wide margin; the monolithic miter from 50 instructions, two-safety without relational cuts,
and a table compared whole above 16 words are red. The generated table in VOS30 section 9.8 is the
evidence; `vos-capacity-probe decide` prints the conditions that placed the outcome.

## How a row is made honest

Every row carries the guards of VOS30 section 9.4:

* **G1** the AND nodes in the miter's cone are *measured from the AIG*; a collapsed row (an
  identical pair of circuits, a constant fold, a propagation-only refutation) is labelled and
  excluded from every statistic. B1 *must* collapse.
* **G2** liveness is *measured on behaviour*: each declared input bit is flipped on random
  assignments (and, for a small cone, decided by a SAT query) and a row whose output cones depend
  on under half of the declared bits is collapsed.
* **G3** every UNSAT row has a paired SAT control: the same instance with one mutated instruction.
  Its model must satisfy the CNF (re-evaluated by a plain evaluator), satisfy the AIG constraints,
  and *replay*: the code side on the real `riscv-simulator`, the reference side on an independent
  concrete evaluator, and the two must differ.
* **G4** `(experiment, knob, seed)` fixes the DIMACS text bit for bit.

And the limits of section 9.5: one child process per row in its own process group, a conflict cap
with proof logging, a 120 s wall timeout, a 2 GiB resident-set cap polled every 50 ms, and the
checker always run under `Limits::default()` (the probe never raises a limit).

## Usage

```text
vos-capacity-probe list
vos-capacity-probe run --tier quick|full [--only A1,B3] [--jobs N] --out results.json
vos-capacity-probe check code/specs/data/vos30-capacity-results.json
vos-capacity-probe table [--check | --write]
vos-capacity-probe decide
vos-capacity-probe merge --base A.json --fresh B.json --experiment E1 [--where field=value] --out C.json
```

* `run --tier quick` is what BUILD runs: the smallest knob of every experiment, five seeds each,
  about ten seconds. It asserts verdicts and controls, never timings.
* `run --tier full` is the recorded offline run (hours). Its output is committed only after a named
  reviewer has regenerated it on a stated host; `dirty_tree`, `binary_sha256` and the regeneration
  banner are **self-reported**, so that review is a process control.
* `check` validates every row against the schema and the guards, then **re-runs every quick-tier row**
  and compares the instance digest, the verdict, the control and the conflict count.
* `merge` refreshes a subset of the committed rows from a fresh `run` (VOS30 section 9.2): the
  other rows stay byte-identical, a dirty fresh run or a changed row identity is refused. Use it
  when `check` reports `instance_sha256 differs` on the E1 `vos-sched-fp-bitmap` rows after that
  crate's generated document changed (VOS-D103): commit, `run --tier full --only E1 --out F`,
  `merge --base R --fresh F --experiment E1 --where fixture=vos-sched-fp-bitmap --out R`, then
  `table --write`.
* `table` renders the generated block of VOS30 section 9.8 (maximum over seeds, banner and the six
  validity limits first); `table --check` fails on drift, on a missing block, or on a section 8.5
  decision that the rows do not give.

## Where it fits

```text
   bit-blaster  cdcl-sat  drat-check  riscv-simulator  riscv-encoder  warrant-grammar
        \          |          |             |               |              /
         +---------+----------+--- vos-capacity-probe -------+-------------+
                                        |
        code/specs/data/vos30-capacity-results.json   ->   VOS30 section 8.5 (the decision)
```

The E1 rows `include!` the committed generated harnesses of the real scheduler
`vos-sched-fp-bitmap` (N = 8) and of the narrowed fixture `vos-probe-ready` (N = 10, a binder
product of 393,216) and drive their `exh_*` entry points in process.
