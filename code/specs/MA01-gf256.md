# MA01 — GF(256): Galois Field GF(2^8) Arithmetic

## Overview

**GF(2^8)** — read as "GF of 2 to the 8th" or "GF of 256" — is a finite field
with exactly 256 elements. The elements are the integers 0 through 255, but the
arithmetic is very different from ordinary integer arithmetic.

### Why Finite Fields?

Three important algorithms in modern computing rely on GF(256):

1. **Reed-Solomon error correction** — Used in QR codes, CDs, DVDs, hard drives,
   and deep-space communication. RS codes treat data bytes as field elements and
   perform polynomial arithmetic over GF(256) to add redundancy that can detect and
   correct burst errors.

2. **QR codes** — The error correction codewords in a QR code are a Reed-Solomon
   code over GF(256). A QR code can survive up to 30% damage thanks to this.

3. **AES encryption** — The AES SubBytes step (the S-box) and the MixColumns step
   use arithmetic in GF(2^8) with the AES polynomial `x^8 + x^4 + x^3 + x + 1`.

This package implements GF(256) with the **Reed-Solomon primitive polynomial**
`x^8 + x^4 + x^3 + x^2 + 1` (= `0x11D`), which is the standard for most QR and
RS implementations.

### Characteristic 2 Means Add = XOR = Subtract

In **characteristic 2** fields, `1 + 1 = 0`. This sounds strange, but it is
consistent: if `1 + 1 = 0`, then `1 = -1`, so subtraction is the same as addition.

Concretely, for **bytes** (elements of GF(2^8)):

```
add(a, b) = a XOR b
subtract(a, b) = a XOR b        ← same operation!
```

This is because each bit of a byte is an element of GF(2) = {0, 1}, and in GF(2),
`1 + 1 = 0 mod 2`. The XOR of two bytes performs GF(2) addition on each bit
independently.

This means you never need a carry bit for addition in GF(256) — XOR is exact.

## The Primitive Polynomial

The elements of GF(2^8) are polynomials over GF(2) of degree ≤ 7:

```
a₇x⁷ + a₆x⁶ + a₅x⁵ + a₄x⁴ + a₃x³ + a₂x² + a₁x + a₀
```

where each `aᵢ ∈ {0, 1}`. This gives 2^8 = 256 elements.

To multiply two such polynomials, the product can have degree up to 14. We reduce
it modulo an **irreducible polynomial** of degree 8, just as integers modulo a prime
give a finite field.

We use the **primitive polynomial**:

```
p(x) = x^8 + x^4 + x^3 + x^2 + 1
```

In binary (bit 8 = x^8, bit 4 = x^4, bit 3 = x^3, bit 2 = x^2, bit 0 = x^0):

```
0b1_0001_1101 = 0x11D = 285
```

### Why Irreducible?

A polynomial over GF(2) is irreducible if it cannot be factored into two
polynomials of lower degree. We need irreducibility to ensure that division
is always possible (every non-zero element has a multiplicative inverse).
This is the same reason we use prime moduli for integer fields: `ℤ/pℤ` is a
field only when `p` is prime.

There are 30 irreducible polynomials of degree 8 over GF(2). We choose one that
is also **primitive** — meaning the element `g = 2 = x` (i.e., the polynomial `x`)
is a generator of the entire multiplicative group.

### What "Generates the Full Multiplicative Group" Means

The 255 non-zero elements of GF(256) form a **cyclic group** under multiplication.
A generator `g` satisfies:

```
g⁰ = 1,  g¹ = g,  g²,  g³,  ...,  g²⁵⁴,  g²⁵⁵ = 1  (cycles back)
```

Every non-zero field element appears exactly once in the list `g⁰, g¹, ..., g²⁵⁴`.

With our primitive polynomial `0x11D`, the element `g = 2` is such a generator.
This means we can represent multiplication using **logarithms**:

```
a × b = g^(log_g(a) + log_g(b))
```

which turns a multiplication into two table lookups and an addition modulo 255.
This is fast and avoids complex bit-level polynomial multiplication.

## Log/Antilog Table Construction

We precompute two lookup tables at startup:

- `ALOG[i]` = g^i mod p(x)   — the antilogarithm table, 255 entries
- `LOG[x]` = i such that g^i = x   — the logarithm table, 256 entries (LOG[0] is unused)

### Algorithm

Start with `g = 2`. Repeatedly multiply by `g` (shift left by 1 bit). If the
result overflows a byte (bit 8 is set), XOR with `0x11D` to reduce modulo `p(x)`.

```
ALOG[0] = 1
for i = 1 to 254:
    val = ALOG[i-1] * 2
    if val >= 256:   (bit 8 is set)
        val = val XOR 0x11D
    ALOG[i] = val
```

Simultaneously, invert: `LOG[ALOG[i]] = i`.

### First 10 Entries

| i | ALOG[i] = 2^i mod p | hex |
|---|---------------------|-----|
| 0 | 1                   | 0x01 |
| 1 | 2                   | 0x02 |
| 2 | 4                   | 0x04 |
| 3 | 8                   | 0x08 |
| 4 | 16                  | 0x10 |
| 5 | 32                  | 0x20 |
| 6 | 64                  | 0x40 |
| 7 | 128                 | 0x80 |
| 8 | 29  (256 XOR 0x11D = 256-285=-29? No: 256 XOR 285 = 0x100 XOR 0x11D = 0x01D = 29) | 0x1D |
| 9 | 58  (29 * 2 = 58, no overflow) | 0x3A |

At i=8: `128 * 2 = 256`. Since 256 ≥ 256, XOR with 0x11D = 285:
`256 XOR 285 = 0x100 XOR 0x11D = 0x01D = 29`. So `ALOG[8] = 29`.

### Last 5 Entries

| i | ALOG[i] | hex |
|---|---------|-----|
| 250 | 36  | 0x24 |
| 251 | 72  | 0x48 |
| 252 | 144 | 0x90 |
| 253 | 57  | 0x39 |
| 254 | 114 | 0x72 |

And the cycle: `ALOG[255]` would be `ALOG[0] = 1` again, confirming `g²⁵⁵ = 1`.

## Operations

### add(a, b) and subtract(a, b)

```
add(a, b) = a XOR b
subtract(a, b) = a XOR b
```

No tables needed. XOR is the only operation. Since characteristic is 2, negation
is identity: every element equals its own negation.

### multiply(a, b)

```
multiply(a, b):
    if a == 0 or b == 0:
        return 0
    return ALOG[(LOG[a] + LOG[b]) % 255]
```

The special case for zero is necessary because LOG[0] is undefined (there is no
power of a generator that equals zero).

**Example**: `0x03 × 0x07 = ?`
```
LOG[0x03] = ?   →  2 is g¹, so ... find 3 in ALOG: ALOG[25] = 3
LOG[0x07] = ?   →  find 7 in ALOG: need to compute...
```
(The exact log values depend on the table; the point is the method.)

### divide(a, b)

```
divide(a, b):
    if b == 0: ERROR (division by zero)
    if a == 0: return 0
    return ALOG[(LOG[a] - LOG[b] + 255) % 255]
```

The `+ 255` before `% 255` ensures the result is non-negative when `LOG[a] < LOG[b]`.

### power(base, exp)

```
power(base, exp):
    if base == 0:
        return 1 if exp == 0 else 0      (0^0 = 1 by convention; not an error)
    if exp == 0:
        return 1
    return ALOG[(LOG[base] * exp) % 255]
```

Note: `exp` can be any non-negative integer; we reduce `LOG[base] * exp` modulo 255
because the multiplicative group has order 255.

> **Spec correction (WD-gf256).** An earlier revision of this section said
> `0^0` is an error and listed "`base = 0` and `exp <= 0`" as a failure case.
> Every implementation in the repository (Rust, Python, TypeScript, Ruby, Go,
> Kotlin, Elixir, Lua, Perl, Dart) returns `1` for `0^0`, their own doc
> comments say so, and the Rust test suite pins it. The convention `0^0 = 1`
> is the one that keeps `power(a, e + f) = power(a, e) * power(a, f)` true at
> `a = 0`, so the specification now matches the code rather than the reverse.
> `power` never fails for a non-negative exponent.

### inverse(a)

The multiplicative inverse of `a` satisfies `a × inverse(a) = 1`.

```
inverse(a):
    if a == 0: ERROR (zero has no inverse)
    return ALOG[255 - LOG[a]]
```

Why? Because `a × ALOG[255 - LOG[a]] = ALOG[LOG[a] + 255 - LOG[a]] = ALOG[255] = 1`.

## Verification — GF(256) Spot Checks

These are well-known test vectors for GF(256) with the `0x11D` polynomial:

```
0x53 × 0x8C = 0x01
```
(0x53 is the multiplicative inverse of 0x8C under the 0x11D polynomial)

Note: The well-known pair `0x53 × 0xCA = 0x01` is specific to the **AES**
primitive polynomial `x^8 + x^4 + x^3 + x + 1 = 0x11B`. AES uses a different
polynomial than Reed-Solomon. With our 0x11D polynomial, `inverse(0x53) = 0x8C`.

```
g^255 = 1
```
(The generator has multiplicative order exactly 255)

```
x × inverse(x) = 1,   for all x in 1..255
```
(Every non-zero element has a multiplicative inverse)

```
add(x, x) = 0,   for all x
```
(Characteristic 2: every element is its own additive inverse)

```
multiply(x, 1) = x,   for all x
```
(1 is the multiplicative identity)

## Rust implementation (`code/packages/rust/gf256`)

This section is the contract the Rust crate is verified against. It records
what the code *does*, including where that differs from the prose above or from
the README.

### Field definition

Elements are the bytes `0..=255` (`u8`). The field is `GF(2)[x] / p(x)` with
`p(x) = x^8 + x^4 + x^3 + x^2 + 1 = 0x11D`, the Reed-Solomon / QR polynomial.
It is irreducible and primitive: `2` generates the 255 non-zero elements
(`power(2, e)` for `e = 0..=254` are pairwise distinct and non-zero;
`power(2, 255) = 1`). It is **not** the AES polynomial `0x11B`, in which `2`
has order 51, `0x53 * 0xCA = 1` and `0x57 * 0x83 = 0xC1`. Under `0x11D`:
`0x53 * 0x8C = 1`, `0x53 * 0xCA = 0x8F`, `0x57 * 0x83 = 0x31`.

### Public operations

| Export | Signature | Contract |
|---|---|---|
| `ZERO`, `ONE` | `const u8` | `0`, `1` |
| `PRIMITIVE_POLYNOMIAL` | `const u16` | `0x11D` |
| `add(a, b)` | `(u8, u8) -> u8` | `a ^ b`; total |
| `subtract(a, b)` | `(u8, u8) -> u8` | `a ^ b`; total; equal to `add` for every input |
| `multiply(a, b)` | `(u8, u8) -> u8` | polynomial product mod `0x11D`; `0` if either operand is `0`; total |
| `divide(a, b)` | `(u8, u8) -> u8` | `a * b^-1`; `divide(0, b) = 0` for `b != 0`; **panics** when `b == 0` (`"GF256: division by zero"`), including `divide(0, 0)` |
| `inverse(a)` | `(u8) -> u8` | `a^-1`; **panics** when `a == 0` (`"GF256: zero has no multiplicative inverse"`) |
| `power(base, exp)` | `(u8, u32) -> u8` | `base^exp`; `0^0 = 1`, `0^e = 0` for `e > 0`, `a^0 = 1`; reduces the exponent modulo 255 through the log table; total over the whole `u32` range (the product `LOG[base] * exp` is computed in `u64`, at most `254 * (2^32 - 1)`, so it cannot overflow) |
| `Field::new(poly: u16)` and its methods | see below | not covered by the Warrant document |

Error behaviour is therefore: **no `Result`s anywhere; `divide` by zero and
`inverse` of zero panic.** There is no error type. Downstream callers that need
a recoverable error must check the operand first. The Warrant document models
the two panics as `Err(Gf256Error.DIVIDE_BY_ZERO)` /
`Err(Gf256Error.ZERO_HAS_NO_INVERSE)` through a binding-level normalisation
(`panic_to_error`), the same device VER26 uses for `ct_select_bytes`; the
export itself still panics, and `ensures no_panic` in the document therefore
holds only at the normalised level.

### Table construction

`build_tables` starts at `val = 1` and for `i = 0..255` records `ALOG[i] = val`
and `LOG[val] = i`, then doubles `val` and XORs `0x11D` when bit 8 appears;
afterwards `ALOG[255] = 1`. `LOG[0]` stays `0` and is never read: every
operation guards zero first. Tables live in a `static OnceLock<Tables>`; the
first call of `multiply`, `divide`, `power` or `inverse` pays about 255
iterations, later calls are O(1). `add` and `subtract` never touch the tables.
Construction is thread-safe (`OnceLock`) and allocation-free (the tables are
inline arrays). The tables themselves are private; their correctness is
observed through the operations (the generated claims `generator_has_order_255`
and `generator_powers_are_distinct` fail on any repeated or missing `ALOG`
entry, `multiply_matches_peasant_model` fails on any wrong product, and the
`generator-shift` sabotage models an off-by-one `ALOG` index).

### `Field` (parameterised polynomial)

`Field::new(poly)` stores `poly` and uses only its low byte as the reduction
constant; operations are table-free shift-and-XOR. `Field::new(0x11D)` agrees
with the module functions; `Field::new(0x11B)` is the AES field.
**Gaps, recorded not fixed:** (1) `Field::new` performs no validation: a
polynomial of degree other than 8 (bit 8 clear or bits above it set) or a
reducible one silently yields an arithmetic that is not a field, and
`Field::divide`/`inverse` (computed as `a^254`) are then wrong without any
error; (2) `Field` is outside the Warrant document, so none of its behaviour is
covered by generated evidence. Both are follow-ups.

### Constant-time status (CWE-208)

**Not constant time, and not claimed to be.** `add`/`subtract` are a single
XOR and have no data-dependent branch or memory access. `multiply`, `divide`,
`power` and `inverse` (a) branch on `a == 0 || b == 0` and (b) index `LOG` and
`ALOG` with operand-derived values: secret-indexed table lookups whose latency
depends on cache state. `Field` multiplication branches on `bb & 1` and
`aa & 0x80` (branchy shift-and-XOR). The Warrant document labels every operand
`secret` to state the threat model (GF(2^8) is the arithmetic of AES), but no
constant-time proof is live: the CWE-208 row in the assurance report is
*applicable and unaddressed*. A hardened implementation would replace the
table path by the branch-free `Field` loop or a bitsliced multiplier and add a
2-safety proof; that is out of scope here.

### Verification status (Warrant-derived)

`code/specs/gf256.warrant` is the specification of the public operations above;
`code/packages/rust/gf256/tests/generated/warrant_evidence.rs` is generated from
it (and `evidence.bindings`), and `BUILD` fails when it drifts. The document
states, over `U8` (the whole domain is enumerable):

* **additive group**: commutative, associative (all 2^24 triples), identity
  `0`, `a + a = 0`, equal to a bit-level XOR *model* (`xor1..xor8`, built from
  comparisons and `+`/`-` because Warrant v0 has no bitwise operator), and
  `subtract = add`;
* **multiplicative structure**: commutative, associative (2^24), identity `1`,
  zero absorbs, no zero divisors, distributive over `add` (2^24), and equal for
  *every* pair to an independent shift-and-add model `gmul`, which is what pins
  the reduction polynomial (every field law also holds in the AES field);
* **division and inverse**: `divide(a, 0) = Err`, `divide(multiply(a, b), b) =
  Ok(a)`, `divide(a, a) = Ok(1)`, `inverse` equal to `divide(1, a)` (and
  `Err` at `0`), the unique right inverse, an involution, and equal to
  `power(a, 254)`;
* **power**: `a^0 = 1`, `a^1 = a`, `0^e`, `a^(e+1) = a^e * a`, `a^255 = 1`,
  exponent reduction modulo 255 up to the `u32` boundary, `a^(2e) = (a^e)^2`,
  non-zero results, Frobenius `(a+b)^2 = a^2 + b^2`, and the order and
  distinctness of the powers of 2.

What Warrant v0 cannot say, stated precisely rather than approximated:

1. **bitwise XOR** is not a primitive; the document builds it from comparisons
   (`xor1..xor8`, one per bit) and checks `add` against it exhaustively;
2. **no `U32`**: `power`'s exponent is `u32` in Rust, declared `U64` with the
   refinement `exp <= 4294967295`; the evidence harness converts and panics
   (a harness bug, never a claim result) on a larger value, and no claim
   quantifies over it;
3. **`rejects` for a panicking export**: `divide`/`inverse` declare their
   rejection with `rejects ... with Gf256Error...`, which the binding realises by
   catching the panic; the export's own `assert!` text is not checked;
4. **the tables**: private, observable only through the operations;
5. **`Field`** and **`PRIMITIVE_POLYNOMIAL`** are not operations of the document.
   (`PRIMITIVE_POLYNOMIAL` is pinned indirectly: a wrong constant makes
   `build_tables` produce a different `multiply`, which `gmul` rejects.)

Binder refinements may use models only, not operations (the generator rejects an
operation inside a refinement): an admission predicate evaluated by a faulted
adapter would change which cases a negative control admits.

### Cross-language expectations

All ports must agree on: the polynomial `0x11D`; `add = subtract = XOR`;
`multiply` as the log/antilog product (or any equal function: the claims are
extensional); `power(0, 0) = 1`; `power` total for non-negative exponents (the
exponent type differs: `u32` in Rust, `int` elsewhere, so a port taking a wider
integer must reduce modulo 255 without overflow); `divide(_, 0)` and
`inverse(0)` are errors, *raised as that language's idiomatic failure*
(panic, exception, error value) rather than returning a value. The Warrant
document is language-neutral; what a port needs to reuse it is (a) a binding
file mapping the six operations to its exports and normalising its failure
mechanism, and (b) a generator target for its language (the evidence generator
emits Rust only today). Method names differ (`pow` in Kotlin, `inv` in several
ports), so bindings are per language.
