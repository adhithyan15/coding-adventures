# A decompressor's memory and output are set by its stream, so cap the delivered bytes and store dictionary entries as links, never as strings

**What went wrong.** `lzw::decompress` was already hardened against the header (SEC-001: it sized nothing from `original_length` and stopped when that many bytes were out), and it was still a bomb. A 15 KB stream of "tricky token" codes (the code for the entry being built, whose string is the previous string plus one byte) expands to about 40 MB, a 128 KB one to two gigabytes, and the header can simply declare `0xFFFFFFFF`. Worse, every dictionary entry was its own `Vec<u8>`, and each entry in such a chain is one byte longer than the one before it, so the dictionary held `k^2/2` bytes for `k` codes: as large as the output, doubling the peak (41 MB live for a 12 MB output). The backlog had recorded this as "needs `max_output`, an API change across ports" and parked it, so it stayed open for a whole conversion cycle. It surfaced the moment the Warrant document tried to write `output` and `heap` rows: the only sound ratio for a 16-bit code standing for a 65,279-byte string is 32,768, which allows 2 GB from 64 KB, i.e. says nothing.

**Fix.** Two contained changes and no API change. Dictionary entries became `(prefix code, first byte, last byte, length)` links, 8 bytes each (at most 512 KiB for the whole dictionary), and the string is written once, into the output, by walking the chain from its end. Delivered output is capped (`MAX_OUTPUT_LEN`, 16 MiB) and exceeding it is an `Err`, checked before the entry is written; only *delivered* bytes count, so a short declared length still stops the decoder early. The cap is a constant, not a `max_output` parameter: that parameter is still the right API (backlog LP-003) and is the owner's decision.

**Do differently.** For any decoder, write down three numbers before reviewing it: bytes delivered per input byte, bytes of memory per delivered byte, and what the attacker controls to change either (the header is usually the least of it). A ratio that cannot be bounded below the machine's memory needs an absolute cap that fails closed, and a per-entry `Vec` in a dictionary whose entries extend each other is a quadratic structure. Keep the old implementation in the tests as a reference and compare Ok/Err and every byte on seeded garbage when you change how it stores things, and build the bomb as a real stream in a test (here a bit packer and a 20-line chain) instead of arguing that it is possible.
