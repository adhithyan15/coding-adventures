# VOS03 -- The Component Shape Checker (`vos-shape-check`)

**Status:** Draft, specified before the code (backlog VOS-D002, lexical half).
The image-level companions (no path to the panic handler, static stack bound)
are **not** in this document's scope; they arrive with VOS-026 and VOS-028.

**Layer:** Tooling, below VOS01 and VOS02. VOS01 section 1.4 defines the shape
rules SH1-SH15 and names "one new, VOS-owned lexical check"; VOS02 section 4.6
adds SH17 and SH18 (VOS-039b-2a adds SH19, the command-type rule), section 7.2-7.3 the static file and manifest bans and the
central evidence-feature list, section 6.8 the parser caps, and section 10
places the tool at `code/packages/rust/vos-shape-check`. This document is the
exact contract of that tool: inputs, which rule binds which crate, the precise
lexical check of each rule, what it cannot see, the report and the exit codes.

**Parent:** [VOS01](VOS01-component-contract-model.md) sections 1.4 and 1.6,
[VOS02](VOS02-interface-contracts-and-profile-linking.md) sections 4.6, 6.8,
7.2, 7.3 and 10.

## 0. What a pass means

The check is **lexical**, in the sense of VER08a section 8: a pass means *no
occurrence the lexer can see*. It reads tokens and the text of `Cargo.toml`;
it never expands a macro, resolves a name, or runs anything. A lexical check
can be too strict (a false positive: a harmless token that looks like a
violation) and it can be too weak (a violation it cannot see). Every rule below
states which of the two it risks, and section 6 collects what it cannot see.
Those residues are exactly the **image-level companions** (VOS-026, VOS-028)
and the **spine audits** (VOS-D024): the shape check narrows the review, it
does not replace the proof on the image.

Bias: where a token is ambiguous the check **fails** (reports). A contributor
rewrites the line; nobody reviews a hidden violation.

**Architecture: the repository's grammar-driven crates, not a hand-written
lexer or parser.** The repository forbids hand-written lexers and parsers, so
`vos-shape-check` is a thin wrapper:

| Input | Read with | What the wrapper adds |
|---|---|---|
| `src/**/*.rs` | `lexer::GrammarLexer` on the RS01 lexical pair `code/grammars/rust/rust1.97.0-e<edition>.tokens` (RS01 section 4; differentially tested against `rustc` 1.97.0; generated by `code/scripts/rust_lexical_pairs.py`, never edited here), edition from `[package] edition` (2021 or 2024, the only ones SH4 allows) | the two RS01 C3 hooks (`rust_strip_shebang`, `rust_block_comments`, RS01 section 4.3, which no crate implements yet) as small adapters; `r#ident` normalisation; the `1.` float; `::`, `->`, `=>`, `..` merging; a bound of 256 on block-comment depth (the engine's group stack is unbounded, RS01 section 4.3) |
| `Cargo.toml`, `vos.toml` | `coding-adventures-toml-parser` (`toml.tokens`/`toml.grammar` through the same generic lexer and parser, recursion cap 165) | flattening every spelling of a key to one path; **duplicate keys fail closed** (the grammar crate accepts them: key uniqueness is a pass it does not run); **escapes fail closed** (the TOML lexer strips quotes but leaves `\u0061` undecoded, so a basic string with a backslash, as a key or a value, is refused rather than decoded by a second implementation) |

The structural layer on top of the tokens (item extents, headers, impl types,
the call graph, the ghost-module shapes) is heuristic code over a token stream,
because RS01's pairs are today lexical/token-tree level only; it will move onto
RS01's syntax grammar when those pairs land (backlog VOS-D038). **One lexer per
run:** `GrammarLexer::new` compiles every pattern (about 175 ms in a release
build per RS01 section 4.1; measured here at 0.09 s for the whole tool on a
small crate, and 0.7 s in an unoptimised build) and cannot be reused for a second
source, so all files of a run are joined into one source and lexed once, separated
by a boundary line. The split is **checked, not trusted**: the boundary identifier
must come back as an ordinary identifier token on exactly the expected line, once
per boundary; a boundary swallowed by an unterminated construct or forged inside a
file refuses the whole batch (fail closed). A left-to-right lexer that lexed the
boundary as a plain identifier was in its start state there, so the text before it
is what that file lexes to alone. VOS02 section 10 says the tool reuses the VER08a
lexer; VER08a's is private and `ca-capability-analyzer` must not be edited (VER29
section 11.2), and the owner rule since then is to use the grammar-driven crates
(backlog VOS-D029, superseded). VER08a `CAP002` remains a second line for `unsafe`,
asm and foreign linkage.

**Every scan that gives up is VT03.** A header, generic list, where clause or
type that is over its cap (4,096 tokens), runs into the next item, or ends where
the file does, is a **VT03** finding and the run FAILs: a structural scan never
skips an item it could not read (that would hide its body).

## 1. Inputs

A run checks **one crate directory**. It reads, nothing else:

| Input | Where | Cap |
|---|---|---|
| `Cargo.toml` | crate root; required | 64 KiB |
| `vos.toml` | crate root; optional (absent means class K, kind unspecified); TOML | 4 KiB, at most 16 key lines, 1,024-byte lines (VOS02 section 6.8) |
| every `*.rs` file under `src/` | recursive, depth at most 16 | 1 MiB each, 512 files and **1 MiB in total** (all tokens of a crate are held at once; the total is enforced while walking) |
| the names of the entries of the crate root | to find `build.rs`, `.cargo`, `rust-toolchain*` | 4,096 entries per directory, 16,384 in all |
| the central evidence-feature list | an argument; default `ghost`, `cov` (VOS02 section 7.3) | 64 names |

Files outside `src/` (`tests/`, `benches/`, `examples/`) are **not read**: they
are not part of the shipped library, and `tests/generated/` evidence harnesses
may use `std`, `unwrap`, floats and the rest. This is a trust statement, not a
proof: those files RUN in the evidence build, so a harness that lies about the
code under test is outside this check (the generated document and its digest,
VOS02 R1-R4, are what bind the harness). The dev-dependencies they use are an
allowlist (SH12), and whether the harness sources should themselves be scanned
is backlog VOS-D035.

**The sibling-crate pattern for Warrant checks.** The allowlist is closed, so a
class K contract or component crate cannot depend on the Warrant tooling
(`coding_adventures_warrant_grammar`) even in `[dev-dependencies]`. A contract package
that wants its Warrant text parsed, type-checked and evaluated before `vos-link gen-doc`
exists (VOS-033) puts those tests in a test-only sibling crate with `class = "H"` in its
`vos.toml`, which depends normally on the contract crate (so the build graph reruns it
when the contract changes) and on `warrant-grammar`. `vos-sched-contract-check` was the
first (VOS10 section 12); `vos-link check-contract` (VOS-039b-1, VOS02 D-GD11) replaced it, and no
new contract needs a sibling crate.

**`#[cfg(test)]` items are masked.** An item whose attribute list contains
exactly `cfg(test)` is removed from the token stream before any rule runs. It
is not compiled into an image or into the generated evidence (the evidence
harness links the library without `cfg(test)`). The mask is a trust decision
and is stated here so it is not discovered: a `cfg(test)` item is *invisible* to
every rule below.

### 1.1 `vos.toml` (VOS02 section 7.3, bounded)

```text
# comment lines start with '#'; blank lines are ignored
class = "K"                      # K, C, S, M, P or H; default K
kind  = "production"             # contract, production, reference, any, spine, hal or profile
evidence-features = ["ghost"]    # names that must be in the central list
coverage-floor = 95              # integer percent of line coverage the BUILD gate enforces (VOS04 5.6)
excused-controls = [{ id = "warrant/m/negctl/exhaustive/init/field-flip", reason = "VOS-D098" }]   # optional (VOS04 5.6)
```

Grammar: the file is TOML (read by the TOML crates, section 0) restricted to
top-level keys, `class` and `kind` (double-quoted strings from the closed
sets above), `evidence-features` (an array of 1 to 32 byte strings, at most
64) and, since VOS-039a, `coverage-floor` (an integer 0 to 100; the shape checker
only reads it, `vos-link check-component` and the BUILD coverage line enforce it,
VOS04 section 5.6) and `excused-controls` (optional; an array of 1 to 16 inline tables `{ id, reason }`: `id` 1 to 128 bytes of `[A-Za-z0-9_/.-]`, distinct; `reason` a backlog row, `VOS-D` and three digits, which `vos-link` requires to exist and be open; never an empty array). A table, a dotted or unknown key, a duplicate key, a value of the wrong
type or outside its closed set, a backslash anywhere, non-ASCII, more than 16
key lines, a file over 4 KiB or a line over 1,024 bytes, and anything the TOML
grammar refuses, is rule **VT01**. The
**class tag lives here, not in the README** (VOS01 section 1.6 and VOS02
section 10 say README; backlog VOS-D030): a tag relaxes rules, so it must sit
on the CODEOWNERS authority list of VOS02 section 7.4 (which already contains
each crate's `vos.toml`), and a prose file is not parsed.

`kind = "any"` requires the package name to end in `-any`, and a package named
`...-any` must declare `kind = "any"` (**VT02**). The other direction of the
name lint (a production crate that carries an `any` block) is evidence, not
lexical, and belongs to `vos-link` (VOS02 section 3.1).

## 2. Which rules bind which class

VOS01 section 1.6, as data. SH16 is a profile-level gate (VOS02 section 7) and is
not checked here. P and H crates have no shape rule (only VT01 to VT03).

| Class | Rules checked |
|---|---|
| **K** (default) | SH1-SH15, SH17, SH18 (and SH19 when `kind = "contract"`, below) |
| **C**, **S** | SH2-SH11, SH13-SH15, SH17, SH18 |
| **M** | SH2-SH9, SH11, SH13-SH15, SH17, SH18 (exempt SH1, SH10, SH12) |
| **P**, **H** | none |

SH17 and SH18 follow SH13 (the ghost face), which binds K, C, S and M.

**SH19 is bound by kind, not by class** (VOS-039b-2a): it is checked exactly when `vos.toml`
declares `kind = "contract"`, whatever the class, and never otherwise. `binds()` is not
consulted for it. The question it asks is not "which shape does this class need" but "this
crate is the one place the command vocabulary lives" (VOS04 section 3, requirement 1).

The table is one function in the code; a change of VOS01 section 1.6 is a one-line
edit. Two disagreements between documents are recorded, not resolved here:
EMU00 section 7.5 calls class M "exempt from the no-panic shape rules" where
VOS01 section 1.6 exempts only SH1, SH10 and SH12 (so SH8 binds M here), and
the literal M row binds SH6, SH7 and SH11 although the wrapped simulators loop,
divide and use `f64` (backlog VOS-D031).

## 3. Report and exit codes

```text
vos-shape-check: crate vos-ready-bitmap, class K (vos.toml), kind production
SH7 src/lib.rs:12 division operator `/`; RV32I has no divide (use shifts and masks)
SH8 src/lib.rs:20 `unwrap` is a path to a panic
result: FAIL, 2 findings
```

One finding per line, `RULE FILE:LINE MESSAGE`, sorted by file, line, rule id
(numeric order, then `VT`) and message, duplicates removed, so the report is
byte-identical across runs and machines. The last line is `result: PASS, 0
findings` or `result: FAIL, N findings`. At most 1,000 findings are printed; if
there are more, a `VT03` line says so (the result is FAIL regardless).

| Exit | Meaning |
|---|---|
| 0 | PASS: no findings |
| 1 | FAIL: one or more findings, including every content-level failure (a file that does not lex, a cap exceeded by content) |
| 2 | **no verdict (blocks, like 1):** usage error, a missing `Cargo.toml`, or the filesystem could not be read safely (a symlink or non-regular file under the crate, an I/O error, a file over its cap before reading, non-UTF-8 text) |

**Every non-zero exit blocks.** Exit 2 means the tool could not look, which is
never a pass: a CI wrapper must fail the job on any non-zero status and must
never treat 2 as "skipped" or "not applicable".

**Fail closed.** A source file that does not lex (unterminated string or
comment, unbalanced `() [] {}`, a character the lexer cannot classify, more
than 262,144 tokens) is **VT03** and the run FAILs; the file is never "skipped".
A `Cargo.toml` the TOML grammar refuses, with a duplicate key, or with an escape in a basic string is VT03 too.

**Caps in the binary.** The binary refuses (exit 2) a `Cargo.toml` or `vos.toml`
over its cap before reading; the library, given the same text, reports VT01 or
VT03 (exit 1). Both are fail closed.

**Filesystem (binary only).** The library is pure (text in, report out). The
binary reads with the VOS02 section 6.8 discipline: it `lstat`s every path and
refuses a symlink at any entry it visits; it opens a file with `O_NOFOLLOW |
O_NONBLOCK` (inlined constants for macOS, FreeBSD and Linux, no dependency) and
then checks the **open handle**: a regular file and, on Unix, the same `dev` and
`ino` the `lstat` saw, so a swap between check and open is refused rather than
trusted and a FIFO cannot hang the open; it checks the size before reading and
bounds the read after it; it enforces depth, per-directory entries (4,096),
total entries (16,384) and total bytes **during** the walk; and it never writes.
On a case-insensitive filesystem `Lib.RS` is compiled and `Build.rs` is run by
Cargo, so an entry whose lower-cased name ends `.rs` but whose exact name does
not, and two entries that differ only in case, are refused (exit 2); `build.rs`,
`.cargo` and `rust-toolchain*` are matched case-insensitively (SH15). Non-Unix
platforms have no `O_NOFOLLOW` here and rely on the `lstat` and open-handle
`is_file` checks only.

## 4. The lexical rules

Tokens come from the RS01 lexical pair (section 0): identifiers (a raw
identifier `r#name` is **normalised to `name`** unless `name` is a keyword, so
`o.r#unwrap()` is `unwrap` and `r#unsafe` stays a non-keyword identifier),
lifetimes, numbers (integer or float), strings and characters, and punctuation.
A float may end in a dot (`1.` is a float; `1..2` and `1.max(2)` are not; the
grammar composes it, RS01 case 10). A first line `#!...` is a shebang and is
skipped only when the next significant token after `#!` (past whitespace and
NON-doc comments) is not `[`: `#! [attr]` is an inner attribute, `#! /** d */ [a]`
a shebang (RS01 section 4.3). A file that begins `---` (frontmatter) is
refused. Comments and the contents of strings are never code; a block comment
nests to at most 256. The contents of an attribute (`#[...]`, `#![...]`) are
examined only by the attribute rules. `::`, `->`, `=>` and `..` are single
tokens; every other punctuation mark is one token that records whether the next
token is punctuation with no space between (so `<<`, `>>`, `/=` are recognised
by adjacency; whether `>>` closes generics or shifts is the rule of SH9).
Anything the grammar lexer refuses (an unterminated literal, a reserved
prefix, a bad exponent such as `1e`, an unterminated or over-deep block
comment, a boundary that was swallowed) is **VT03**. *Rule text cites VOS01 or
VOS02; the second column is the exact lexical check.*

| Id | The check | Risk and what it cannot see |
|---|---|---|
| **SH1** | (a) `src/lib.rs` carries `#![no_std]` as a **crate-level** inner attribute (the leading run of `#![..]` at the start of the file; one inside `mod m { }` applies to `m`); (b) the identifier `extern` followed by `crate` anywhere; (c) the identifier `std` or `alloc` followed by `::`, or following `use`, unless it is a later segment of a path whose previous segment is a non-keyword identifier (`core::alloc::Layout` passes; `use ::std::..` and `return ::std::..` do not) | (a) accepts the attribute text, not its effect (a `cfg_attr` spelling is rejected, so it only errs strict) |
| **SH2** | (a) the identifier `unsafe`; (b) `extern` not followed by `crate` (foreign linkage); (c) `asm`, `global_asm`, `naked_asm`, `llvm_asm` followed by `!`; (d) an attribute naming `link` or `link_name` (**SH2, not SH15**); (e) exactly `#![forbid(unsafe_code)]` as a crate-level inner attribute of `src/lib.rs` (`forbid(unsafe_code, x)` is not it); (f) any `allow`, `warn`, `deny`, `expect` or `cfg_attr` attribute naming `unsafe_code` (a waiver) | `unsafe` produced by a macro is excluded because SH15 bans non-core macros. `forbid` is required, not `deny`, because an inner `allow` overrides `deny` |
| **SH3** | (a) the identifier `static` (a lifetime `'static` is a lifetime token); (b) `thread_local` followed by `!`; (c) a `const` item (`const NAME: T`, `const _: T`, associated or trait) whose type tokens contain an interior-mutability name: `Cell`, `RefCell`, `UnsafeCell`, `OnceCell`, `LazyCell`, `OnceLock`, `LazyLock`, `Mutex`, `RwLock`, `SyncUnsafeCell`, any `Atomic*`, **or** the name of a `struct`, `enum`, `union` or `type` of the same crate whose definition mentions such a name (a worklist over a reverse map, linear) | (c) is by name: an interior-mutable type of another crate under a name outside the list passes. The type scan of a const is bounded (256 tokens) and a type definition is read to its end or the next item keyword (4,096 tokens at most) |
| **SH4** | (a) the identifiers `dyn`, `Fn`, `FnMut`, `FnOnce`; (b) `fn` immediately followed by `(`; (c) a closure: a `|` or `||` whose previous token is `(`, `,`, `=`, `{`, `;`, `[`, `:`, `=>`, `->`, `&`, `*`, `!`, `return`, `move`, `async`, `else`, `in`, `break`, `yield`, `await`, or the keyword `move` followed by `|`; (d) `package.edition` is the literal `"2021"` or `"2024"` | (c) is a heuristic and a leading `\|` in a pattern after `(` or `{` is a false positive. A function item coerced to a pointer without a written type is invisible |
| **SH5** | the name-resolved lexical call graph is acyclic: **every strongly connected component of two or more functions, and every self-loop, is reported** (iterative Tarjan, O(V+E)). Nodes are `fn` items keyed by (enclosing `impl` or `trait` type, or one synthetic key for an impl on an array, tuple, unit or pointer type, or none) and name. Edges go from the innermost enclosing `fn` to: a bare `f(`; `Self::f(`; `Q::f(`, `Q::<T>::f(` (qualifier BEFORE the turbofish), `Q<T>::f(` and `<Q as T>::f(` (the key (Q, f); every method named `f` if `Q` is a trait of the crate; otherwise no edge); `x.f(` (every method named `f`); a lowercase path `m::f(`. Many call sites of one callee are one edge (deduplicated before resolving). More than 200,000 edges, 4,096 functions, or any `fn`, `impl` or `trait` header that could not be read (VT03, as for every structural scan) fails closed | by name, so unrelated methods called `f` can look like recursion (rename). Calls into other crates, through generic parameters (`<P::Ready as ReadySet>::insert` has qualifier `P`), macros or fn values are invisible: cross-crate recursion is the static stack bound (VOS-028) |
| **SH6** | (a) the identifiers `while` and `loop`; (b) every `for` that is **not inside an `impl` header** (and not `for<'a>`) is a loop and must be exactly `for IDENT in 0..K {` with `K` an integer literal or a path whose last segment is a constant name (`LEN`, `Self::N`); a `for` with no `in`, `0..=K`, a non-zero start, an expression bound or a pattern other than the shape (`for S { a } in ..`) is a finding; (c) a method call or `::` path call whose name is an iterator adaptor: `iter`, `iter_mut`, `into_iter`, `map`, `filter`, `filter_map`, `flat_map`, `flatten`, `zip`, `enumerate`, `rev`, `fold`, `try_fold`, `collect`, `step_by`, `skip`, `skip_while`, `take_while`, `chain`, `sum`, `product`, `any`, `all`, `for_each`, `windows`, `chunks`, `chunks_exact`, `position`, `find_map`, `peekable`, `scan`, `cycle`, `nth`, `count`, `reduce`, `find` | that `K` is the *intended* bound (VOS01 rule 7) is not lexical. (c) is by name and can fire on `Option::map`. **Decided, not denied:** `last`, `max`, `min`, `take` (total, O(1) on integers, options and slices; they iterate only an iterator, which an adaptor above or a range expression produces, and `(0..N).max()` is the residual in section 6) |
| **SH7** | the punctuation `/` or `%` (so `/=`, `%=`); a method or path call whose name is `div`, `rem`, or has `div` or `rem` as an `_`-separated segment (`div_euclid`, `checked_div`, `wrapping_rem`, `div_ceil`), followed by `(` | the operator is seen only as written. A division inside a library the component calls is the image companion |
| **SH8** | (a) a method or `::` path call named `unwrap`, `expect`, `unwrap_err`, `expect_err` or `unwrap_unchecked` (`Option::unwrap(o)` counts); (b) the macros `panic`, `unreachable`, `todo`, `unimplemented`, `assert`, `assert_eq`, `assert_ne`, `debug_assert`, `debug_assert_eq`, `debug_assert_ne`, **except** `assert!` inside a `const _: () = ..;` item whose initializer contains no `fn` or `impl` token; (c) every `[` is an index unless the previous token is on an ALLOWLIST of array-literal, array-type and attribute positions (`=`, `(`, `,`, `;`, `{`, `:`, `#`, `!`, `&`, `<`, `->`, `=>`, `[`, `\|`, `..`, `+ - * / % ^`, a lifetime, or one of the keywords `in return break else if match let as mut ref dyn impl where for move const static type use unsafe yield`): `w.0[i]`, `f()?[i]`, `{..}[i]`, `self[i]`, `g().await[i]`, `b"ab"[n]` are indexes. An index is allowed only if it is exactly one identifier that is the variable of an enclosing `for v in 0..K` loop AND no `let` (including `if let` and tuple patterns) between the loop start and the index re-binds that name, and no match arm pattern before it binds that name (`match n { i => a[i] }`) | that `K` equals the indexed array's length, and every panic inside a called function, are not lexical (image companion). Shadowing by a closure parameter or a nested `for` pattern is not seen (section 6). A loop body over 8,192 tokens exempts no index |
| **SH9** | (a) a shift (`<<`, `>>`, `<<=`, `>>=`) is a finding unless its right operand is an integer literal that is the **whole** operand: the next token must end it (`; ) ] } { , \| & ^ = < > ? : ! =>` or `as`), so `x << 1 + n`, `x << 1.max(n)`, `x << 8 * n` are findings. A `>>` is generic only if **all** hold: two unmatched `<` precede it in the same statement; the OUTER one is a real generic open, which is only after `::` (turbofish), after `impl`, or after a name that follows `dyn`, `for`, `as`, a declaration keyword (`fn struct enum trait type union mod`), `->` or a type-introducing `:`, or, inside such a list, after `<`, `,`, `&`, a lifetime (a `<` after `(`, `=`, or a `,` outside generics is a comparison); the inner one directly follows a type name or `::`; only type-ish tokens (names, `::`, `,`, `&` not doubled, `+`, `:`, lifetimes, groups) lie between the outer `<` and the `>>`; and what follows can follow a type: `, ; ) ] } = + : ?`, `where`, `as`, `for`, plus `(` after a declaration's generics, `{` after a return type or an `impl .. for` / `impl<..>` header, and `::` after a turbofish (never `{` or `::` otherwise). `a < b && c < d >> n`, `a < b || c < d >> n`, `f(a < b, c < d >> n)`, `g(a < b, c < d >> { n })` and `S { f: a < b, g: c < d >> { n } }` are therefore shifts. A `<<` is generic only if its first `<` is a real open (as above), its second `<` closes right before `::`, and the group holds an `as` between type-ish tokens; `1u32 << s > ::core::u32::MAX` and `n << y as u32 > ::core::u32::MAX` are shifts. On any doubt the shift is reported; (b) a method or path call named `pow`, `shl` or `shr` | "provably below the bit width" by a guard is **not lexical**: the shift is reported and rewritten. **Bare `+ - *` are not checked** (VOS-D032): `clippy::arithmetic_side_effects` denied in CI is the second line |
| **SH10** | (a) the identifiers `Vec`, `String`, `Box`, `Rc`, `Arc`, `HashMap`, `HashSet`, `BTreeMap`, `BTreeSet`, `VecDeque`, `BinaryHeap`; (b) `isize`, and `usize` unless it is the cast target in `as usize` or the type of a `const NAME: usize` item or const generic parameter; (c) a reference type: any `&` inside a `fn` signature (from `fn` to the body or `;`, including `&self`), inside a `struct`, `enum` or `union` body, or a `&` followed by a lifetime | an alias (`type Idx = usize;`) is reported at the alias; references local to a function body are not types of `State`, `In` or `Out` and are not reported unless they carry a lifetime |
| **SH11** | the identifiers `f32`, `f64`; a float literal (`1.0`, `1.`, `1e3`, `2f32`, `1_f64`) | exact |

## 6. What this check cannot see (the residue)

1. **Macros.** SH15 bans `macro_rules` and every non-core macro in the crate
   under check, so no macro of the crate can expand into a forbidden item. The
   core macros on the list (`matches!`, `cfg!`, ...) expand into `match` and
   constants the lexer does not see; a macro from another crate does not
   exist (SH12).
2. **Names.** No resolution: SH5 is by name, SH3 and SH10 by type names, SH8's
   panic methods by method name. A type alias to a forbidden type defined in
   another crate and a `use ... as` rename of a banned name outside the lexer's
   patterns are invisible.
3. **Values.** `for i in 0..K` bounds are checked as *spelled*, not by value;
   an index loop bound equal to the array's own length is not checked; the
   guard behind a shift or an index is not evaluated.
4. **Arithmetic.** Bare `+ - *` (SH9) are not detected here; `clippy::
   arithmetic_side_effects` in CI is the other line (VOS-D032).
5. **Callees in other crates.** A panic, a division, a loop or recursion in a
   function the component calls, even in `core`, is invisible: the two
   image-level companions (VOS-026, VOS-028) close this.
6. **Resolution of features and of the build.** What Cargo enables
   (unification, `--features`, `[patch]`) and what the build produces is the
   hermetic recorded build of VOS22 (SH16).
7. **Self-declaration.** A `vos.toml` class tag *relaxes* rules, and a crate
   can write `class = "M"` for itself. The tag is on the CODEOWNERS authority
   list, and `vos-link` must cross-check class and kind against the profile
   and a central crate-to-class registry (backlog VOS-D030). This tool checks
   the tag's syntax and values, not its truth.
8. **`cfg(test)` masking** (section 1) and the files outside `src/`: `tests/`,
   `examples/` and `benches/` are never scanned yet run in the evidence build
   (backlog VOS-D035).
9. **Shadowing and iterators.** An index variable shadowed by a `match` arm,
   a closure parameter or a nested `for` pattern is not seen (only `let`,
   `if let` and `while let`). `(0..N).max()` and `.last()` / `.take()` on a
   range are not denied (SH6), and a range expression used as an iterator
   without `.iter()` is invisible.
10. **Bounds of the scan.** A function or impl header over 1,024 tokens, a loop
    body over 8,192 tokens (no index exempt), a call graph over 4,096 functions
    or 200,000 edges, and a file over 262,144 tokens are refused or reported
    (VT03), never half-checked. Wide generic lists over 256 tokens are not
    recognised as generics.
11. **Filesystem.** Non-Unix platforms have no `O_NOFOLLOW`; the TOCTOU defence
    there is the `lstat` and open-handle `is_file` checks only. A case-folding
    collision cannot be created on a case-insensitive filesystem to be tested.
12. **Host-dependent sizes.** `size_of::<*const u8>()`, `align_of`, `as usize`
    and pointer-width arithmetic differ between the 64-bit evidence host and the
    32-bit image **without any `cfg`**; SH10 allows `as usize` (VOS01 section
    1.3) and nothing here can see which value a program computes. The image
    proofs (VOS-026) and the evidence build's `usize`-free vocabulary are the
    answer.
13. **Cargo-level build configuration.** `[workspace]`, `[patch]`, `[replace]`,
    `[lints]`, `[profile.*]`, `[target.*]` build settings and workspace
    inheritance (`edition.workspace = true` is refused by SH4, nothing else is
    followed) change what is compiled and are VOS22's hermetic build and
    VOS02 section 7.2, not this tool's.
14. **Dependency allowlist by name.** The `[dev-dependencies]` allowlist and the
    contract-crate name pattern of SH12 match **names only**; that a `path` points
    at the intended in-repo crate is `vos-link`'s closed-world check (VOS-D034).
15. **The grammar crates' own limits.** The lexical pair is RS01's and is only as
    good as its differential evidence; `GrammarLexer` cannot be reused for a second
    source (so one lexer is built per run and files are joined with a checked
    boundary); the TOML crate gives no position for a lexical or syntax error
    (the report line is 1), accepts duplicate keys and leaves escapes undecoded
    (this tool refuses both). Logged as VOS-D039 to VOS-D041.
16. **Intended SH9 false positives (the safe direction).** A real nested
    generic whose outer `<` is not in a position listed in SH9 is reported as a
    shift: a tuple-struct field (`struct S(Option<Option<u8>>)`), a type behind
    `&` outside any generic list (`&Option<Option<u8>>`), a nested generic in an
    expression argument list, and a nested generic ending a `where` clause before
    its `{`. Rewrite with a named field, a `type` alias or a `let` with a type
    annotation; the declaration positions (parameters, return types, fields,
    `let x: T`, bounds, `impl` headers, turbofish) stay clean.
18. **SH19 is lexical** (VOS-039b-2a). It reads enum variants from the token stream, so it
    sees what is WRITTEN: a type is accepted only as the five spellings of the SH19 row.
    A `type Addr = usize;` alias is rejected rather than resolved (the check never follows a
    name to its definition across a path or an alias), so the safe direction is a finding,
    never a pass. The command set is every enum of a contract crate; a contract crate that
    wants a non-command enum with a wider payload has none to write (the crate is
    declarations only, VOS10 section 15). The HAL side (the allowlist) is VOS-025a.
    A lexical check never converges against an adversary that can rename things, so it does
    not try: a contract crate's vocabulary is CLOSED (SH19 (d)-(g): no `use`, `mod`, macro or
    item named like a primitive or a Warrant built-in), and the check refuses the construct
    instead of resolving it. What remains is what a flat, import-free, macro-free crate can
    still say, which the spellings of the SH19 row cover. CK10 compares only the NAME of a
    nested same-crate type, not its contents; SH19 judges the contents (VOS-D111). The attribute vocabulary is a closed list too (SH19 (h), VOS-D112), and a contract crate has no dependency to supply a macro (`check-component` CC10).
17. **SH14 spine half, SH16, and the audits of VOS02 section 5** (the
   `impl Profile` block, `site_` claims): VOS-D024, VOS-034 and VOS22.

### 7.1 Tick audit (VOS-039d, closing VOS-D089)

The linearity items above are asserted on a **deterministic step counter** (`src/steps.rs`, `tick()`), not on
wall-clock time (a clock on a shared runner has a fixed lexer-building cost larger than the signal). The counter
sees only the loops that call `tick()`; a scanner loop that forgot to tick could turn quadratic with every
linearity test still green. The **tick audit** is the rule that closes that gap, and a test that enforces it on the
checker's own source.

**The rule.** Every `while`, `loop` and `for` loop in `src/**/*.rs`, outside `#[cfg(test)]` items, does exactly one
of:

1. calls `tick()` (bare or path-qualified: `crate::steps::tick()`) in its **own** body, once per iteration; a tick
   inside a *nested* loop's body does not count for the outer loop (it counts the inner loop's iterations); or
2. carries, on the line immediately above the loop keyword, the comment `// bounded: <reason>` with a non-empty
   reason saying why its trip count is bounded by a constant or by one step of an already-ticked outer loop
   (for example `// bounded: a fixed pair of editions`).

Ticking is the default; `bounded:` is for loops whose bound is true by construction. A loop over a slice, a token
range or any collection whose length follows the input is ticked, never marked.

**How the audit finds loops.** `tests/tick_audit.rs` reads no Rust text of its own: it lexes the crate's sources
with the RS01 grammar-driven lexer, indexes them with `FileCtx` (bracket pairs, the `#[cfg(test)]` mask), and works
on tokens. `while` and `loop` are loops; `for` is a loop only if an `in` token precedes the body's `{` at bracket
depth zero (so `impl X for Y {` and the bound `for<'a>` are not); the body is the first `{` after the keyword that
is not inside a bracket pair; a tick is the token sequence `tick ( )` inside the body. The one piece of text read
directly is the line above the loop keyword (the lexer discards comments, so the marker is not among the tokens).
Negative controls feed the checker synthetic sources: an unticked `while`, `loop` and `for` fail; a tick (bare and
`steps::`-qualified) passes; a `// bounded:` line with a reason passes, without a reason or two lines above fails;
a tick in an inner loop does not excuse the outer one; `impl X for Y`, `for<'a>`, a loop in a string and a loop in
a `#[cfg(test)]` item are not loops.

**Result of the first audit.** 182 loops: 180 tick, 2 are `bounded:` (the retry of `lex_documents`, at most four
attempts; the pair of editions in `check_crates`). The previously invisible paths now count: the lexer adapter
and its comment scan, the shebang scan, `FileCtx::from_tokens`, the outer loop of `mask_cfg_test`, and the rule
passes' outer loops. `tests/tick_audit.rs` also holds linearity tests (n, 4n, 16n) of lexing (plain tokens, many
block comments, comments after `#!`) and of the `cfg(test)` mask (kept attributes, alternating dropped and kept
items).

**Not covered.** Iterator chains (`.iter().map(..).collect()`) and recursion hide work without a loop keyword;
the audit does not see them. A chain over input-sized data in a scanner is a review matter. A tick in a loop
is a convention the audit checks by presence, not that the tick stands for the loop's real unit of work.
