## 0.581.0 (UNRELEASED) — LANG83 PR4 overflow family

- LANG83 PR4 — overflow-checked arithmetic on every backend. `tests/op_conformance.rs` gains fifteen cases for `i64_add_ovf`, `i64_sub_ovf`, `i64_mul_ovf` and `i64_neg_ovf`: exact results at the i64 bounds (`MAX + 0`, `MAX - 1 + 1`, `MIN + MAX`, `MIN - 0`, `MIN + 1 - 1`, `-1 - MAX`, `MIN * 1`, `-2^32 * 2^31 = MIN`, `3_037_000_499²`, `-1 * MAX`, `-MAX`, `-0`), `Trap.Overflow` one step past them after printing (`MAX + 1`, `MIN + -1`, `MIN - 1`, `MAX - -1`, `MIN * -1`, `-1 * MIN`, `2^32 * 2^31`, `3_037_000_500²`, `neg MIN`), an unused-result `i64_add_ovf` after unflushed `write_i64` output that must still trap (mutation-checked: dropping the op from `CIRInstr::is_pure`'s impure list makes the JIT column print `11` and complete), and a `putchar`-only module whose only i64 evidence is the checked op (mutation-checked: without that evidence the JVM concretizer narrows it and the JVM backend refuses `int` operands). New gate `pr4_ops_are_lowered_on_every_backend`. Locally every case compiles on LLVM/WASM/JVM/CLR/BEAM/native and executes on WASM, VM, JIT, LLVM, native and JVM. `concretize_scalar_any_for_jvm` now *derives* its op-side wide-model evidence from the registry (every Op with an `i64` operand type) instead of a hand-kept `["i64_div_floor", "i64_mod_floor"]` list, with a unit test that a module using any of them stays on `i64` and a plain `add` module still narrows. `op_check`'s per-backend test also requires every PR4 op to be `Lowered`, and a new test passes a module using all four through `check_module_for` on every backend.
