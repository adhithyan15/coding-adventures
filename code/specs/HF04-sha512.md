# HF04 — SHA-512

## Status

Portable conformance contract for the repository's from-scratch SHA-512
implementations. This contract follows FIPS 180-4 and is exercised by the
bounded neutral corpus in `fixtures/sha512-v1/cases.txt`.

## Algorithm

SHA-512 consumes an octet string, processes 1024-bit blocks with the 80-round
SHA-512 compression function, and returns exactly 64 digest octets. Hex helpers
return exactly 128 lowercase ASCII hexadecimal characters.

Padding appends `0x80`, zero octets until the message length is 112 modulo 128,
then the original message length in bits as a 128-bit unsigned big-endian
integer. Implementations must preserve both halves of this field. A streaming
counter therefore may not silently wrap after `2^61` bytes. FIPS inputs are
shorter than `2^128` bits; a counter value of `2^125` bytes or greater is an
error before state mutation.

## API contract

Each established lane keeps its language-idiomatic names and return types.
All lanes provide a one-shot digest and lowercase hex helper. Where a streaming
API is present, it additionally obeys these rules:

- updates are incremental and retain at most one partial 128-byte block;
- input bytes are consumed during the call and are not aliased afterward;
- digest/finalization is a non-destructive snapshot;
- updates may continue after a snapshot;
- copy/clone, when exposed, produces independent state;
- an update that would exceed the FIPS message-length domain fails before
  changing the state.

Lanes without an established streaming API are not required to invent one in
this audit. Callers retain ownership of one-shot input containers, and hashing
must not modify them.

## Errors and resource bounds

Public functions accept only the lane's documented byte container. Dynamic
lanes must reject other input types synchronously with a stable exception or
error category; they must not coerce text, numbers, or null values into bytes.
No implementation may delegate to a host cryptography primitive.

The portable corpus is data, not authority. A reader must reject malformed
rows and enforce all of these limits before decoding: 64 rows, 4,096 bytes of
file data, 4,096 decoded input bytes per vector, 128 digest hex characters,
and at most 64 chunk entries. Native test code may use tighter limits. Hashing
work is linear in the input size. Streaming storage is bounded by the eight
state words, one schedule, and one partial block; one-shot implementations may
allocate a padded copy linear in the already-materialized input.

## Neutral conformance corpus

`fixtures/sha512-v1/cases.txt` is the canonical cross-language corpus. `V`
rows cover empty, binary, Unicode-encoded, and both sides of the SHA-512
padding boundary. Chunk plans sum exactly to the decoded input length and are
used only by lanes with streaming APIs. `L` rows exercise the full 128-bit
length-field transformation without allocating messages of those sizes,
including the first low-word carry and the FIPS-domain rejection boundary.

The expected digests are fixed FIPS-compatible witnesses and must not be
regenerated by the implementation under test.

## Capabilities and exclusions

SHA-512 is pure computation and requires no filesystem, network, process,
clock, randomness, environment, device, or secret capability. Existing
capability profiles remain empty.

This contract does not cover SHA-384, HMAC composition, secret custody,
authority policy, host-crypto substitution, or new language ports.

## Established lanes

C#, Elixir, F#, Go, Haskell, Lua, Perl, Python, Ruby, Rust, Swift, and
TypeScript.
