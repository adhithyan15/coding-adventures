# VisiCalc — Mosaic demo

A VisiCalc-style spreadsheet built end-to-end on the Mosaic UI compiler
stack. This is the capstone for the UI work tracked in
[`code/specs/UI26-visicalc.md`](../../code/specs/UI26-visicalc.md) — every
pixel of the rendered UI is generated from the `.mil` / `.mll` / `.msl`
sources in [`mosaic/`](mosaic/); the only hand-written code lives in
[`src/app/`](src/app/).

## What's here

```
code/programs/typescript/visicalc/
  mosaic/
    Grid.mil              — interface (slots + emits) for the spreadsheet grid
    Grid.desktop.mll      — desktop layout (pass-through to the Grid primitive)
    Grid.dark.msl         — dark theme styles
    FormulaBar.mil        — interface for the formula bar
    FormulaBar.desktop.mll — desktop layout (Row + Text + Input)
    FormulaBar.dark.msl   — dark theme styles
  src/
    components/           — GENERATED by scripts/build.sh; do not edit, do not commit
    app/
      state.ts            — AppState + reducer (the only "spreadsheet logic")
      util.ts             — A1 cell-address helpers, viewport-row builder
      App.tsx             — host component (useReducer + Grid + FormulaBar)
      main.tsx            — React 18 root mount
  scripts/build.sh        — runs mosaic-compile to regenerate src/components/
  index.html, package.json, tsconfig.json, vite.config.ts
```

## How to build the components

The Mosaic-generated `src/components/*.tsx` are **not** committed to the
repo; they're regenerated on demand from the source files in
[`mosaic/`](mosaic/). The `scripts/build.sh` driver rebuilds
`mosaic-compile` if needed and invokes it twice (once per component):

```bash
cd code/programs/typescript/visicalc
bash scripts/build.sh
# Writes: src/components/Grid.tsx, src/components/FormulaBar.tsx
```

## How to run the demo

```bash
cd code/programs/typescript/visicalc
npm install
npm run dev       # rebuilds components then starts Vite at http://localhost:5174
```

`npm run dev` runs `scripts/build.sh` first, so the components are always
fresh before the dev server starts.

## Architecture (UI26 §1)

```
.mil + .mll + .msl  (per component, authored by hand)
        │
        ▼
mosaic-compile --backend react
        │
        ▼
src/components/Grid.tsx        ←  generated, do not edit
src/components/FormulaBar.tsx  ←  generated, do not edit

         ┌────────────────────────────────────┐
         │  Host React application            │
         │  (useReducer + AppState)           │
         │                                    │
         │   slots (data ↓)  dispatch (↑)     │
         ├─────────────────┬──────────────────┤
         ▼                 ▼
   FormulaBar         Grid
   (generated)        (generated)
```

Three structural invariants:

1. **Mosaic components are dumb renderers.** They know nothing about
   spreadsheets — they just render the props they're given and fire the
   events declared in their `.mil` interface.
2. **The host owns all state** in a single `useReducer`. Cell values,
   selection, edit state, viewport — all of it.
3. **Formula evaluation is out of scope** for this demo. The host stores
   raw string values per cell and displays them as-is. Replacing that
   with a real expression evaluator is a separate parallel track (see
   the formula-engine work, tracked separately from the UI queue).

## Known limitations of this v1 (deferred to follow-up PRs)

The demo intentionally bumps into several real architecture-level gaps
in the current Mosaic compiler stack. Each is documented so the next
contributor can pick them up:

1. **`list<list<text>>` not yet representable in mosmodel-compiler.**
   UI26 §2.1 calls for `slot viewport-rows : list<list<text>>` so the
   Grid receives an `Array<Array<string>>` (one element per cell). The
   current `mosmodel-compiler::ListInnerType` enum only models flat
   lists (no recursive `List` variant), so the generated Grid prop type
   is `Array<string>` instead. `src/app/App.tsx` uses a
   `// @ts-expect-error` directive to acknowledge the mismatch — the
   architecture is correct; the rows will only render once nested-list
   support lands. Follow-up: add `List(Box<ListInnerType>)` to
   `mosmodel-compiler`, regenerate the components.

2. ~~**Event-union types are not `export`ed by the pipeline emitter.**~~
   *Resolved.* The pipeline emitter now writes `export type GridEvent =
   ...` and `export type FormulaBarEvent = ...` so the host imports the
   shapes directly from the generated component files instead of
   redeclaring them in `state.ts`.

3. ~~**No `placeholder: "..."` on the FormulaBar Input.**~~ *Resolved.*
   moslayout's grammar now accepts double-quoted string literals as prop
   values, and the React Input emitter wires `placeholder` straight
   through to the generated `<input placeholder="...">`. The FormulaBar
   `.mll` carries `placeholder: "Enter formula"` directly.

4. **No formula evaluation.** Cells store and display raw strings.
   `editCommit` is where a real formula engine would plug in; see
   UI26 §11 and the separate formula-engine track for details.

5. ~~**No column-widths binding.**~~ *Resolved.* The Grid emitter now
   reads the optional `column-widths` slot ref (UI26 §2.1) and emits a
   `<colgroup>` mapping each width to a `<col style={{ width: "${w}px" }} />`.
   The VisiCalc host passes `state.columnWidths` through, so both
   header and body cells share a stable per-column width.

6. **No viewport virtualisation.** The host passes the full viewport
   slice; the Grid renders every row it sees. Row-windowing is the
   host's responsibility per UI26 §11.
