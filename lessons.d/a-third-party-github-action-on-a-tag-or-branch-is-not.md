# A third-party GitHub Action on a tag or branch is not pinned — a tag is mutable and a branch is worse

`pypa/gh-action-pypi-publish@release/v1` is a *branch* ref on the action that holds PyPI trusted-publishing OIDC: whoever controls that branch controls a publish with the repo's identity. Same shape for `dtolnay/rust-toolchain@master`, which installs the compiler for every Rust job. Pin release- and publish-path actions to a 40-character SHA with a trailing `# vX.Y.Z` comment so a future bump is reviewable. Verify the SHA maps to the version the comment claims — `gh api repos/OWNER/REPO/tags` — rather than trusting the tag you started from. **Enumerate by what the ref IS, not by the strings you happened to notice.** The first pass here pinned `dtolnay/rust-toolchain@master` and missed `@stable` — also a branch, 8 more sites, including release workflows the same commit had already edited. In one of them the *publisher* got pinned while the *compiler producing the bytes being published* stayed mutable in the same file, which is the higher-value target. `gh api repos/OWNER/REPO/branches` tells you which refs are branches; grepping for the one you thought of does not. Existing pins drift too: a `# stable` pin already in the tree had diverged from the branch it named. **And check that classifier with an exit code, not with output emptiness.** `gh api repos/O/R/branches/REF` prints its 404 body to *stdout* and exits non-zero, so `[ -n "$(gh api ... 2>/dev/null)" ]` counts every missing branch as a branch. That bug had me about to report "all eight refs are branches" when three were; use `if gh api ... >/dev/null 2>&1`. Most `@vN` refs on popular actions are mutable *tags* rather than branches -- still worth pinning, but ranking the work needs the distinction to be right. **And pin the GENERATORS, not just the tree.** `web-app-scaffold-generator` emits a deploy workflow with `peaceiris/actions-gh-pages@v4` baked into a template string, so every scaffolded app re-introduced an unpinned action holding `contents: write`. A sweep that fixes the checked-in files and leaves the thing that writes them has a half-life, not a fix. `grep` the emitters (`--include='*.ts' --include='*.py' --include='*.go'`), not only the workflows. **And that "publisher pinned, builder not" shape recurred, in the same file the lesson was written about.** A later sweep found `publish.yml` still running `PyO3/maturin-action@v1` — a mutable tag — in the two jobs carrying `id-token: write`, three lines from the `pypa/gh-action-pypi-publish` SHA pin that sweep had added. maturin *builds the wheels* that pin then publishes under the repo's PyPI identity, so it is the same "compiler producing the bytes" target, just the Python one. Knowing the shape did not find the instance, because the search was still by remembered action name. Enumerate mechanically instead: list every workflow whose `permissions:` grants `contents/packages/id-token/pages: write`, list every `uses:` in those files, and subtract the ones already matching `@[0-9a-f]{40}`. What is left is the actual work-list, and it does not depend on which action names you happen to recall. **Uncommented pins hide the same way.** The trailing `# vX.Y.Z` is not decoration — a 40-hex SHA with no comment is unreviewable, so nobody reviews it; 13 such pins were sitting in `ci.yml` and `build-ocaml.yml` while the convention was considered applied. `grep -oE 'uses: *\S+@[0-9a-f]{40}( *#.*)?' | grep -v '#'` finds them. **And the mechanical enumeration is only as good as its regex — mine could not see three-segment action paths.** `uses: *[a-zA-Z0-9._-]+/[a-zA-Z0-9._-]+@[^ ]+` assumes `owner/repo@ref` and simply does not match `gradle/actions/setup-gradle@v5`, so the sweep that was written to enumerate mechanically still missed two unpinned third-party actions on release paths — one of them 23 lines below a `subosito/flutter-action` the same commit was pinning, in the same matrix job. A second trap compounds it: filtering "first-party" with `grep -v '^actions/'` misclassifies any three-segment action whose SECOND segment is `actions`. Split on `/` and test `parts[0] == 'actions'`, and allow `[^\s#]+` after `uses:` rather than enumerating path shapes. Parse the YAML for `permissions:` too — six workflows here grant write at JOB level only, which a file-wide grep happens to catch but a top-level-only parse would not. Verified end state, not asserted: zero unpinned third-party refs across all 39 workflows. **And a blanket "every SHA pin needs a trailing `# vX.Y.Z`" broke a contract.** `build-ocaml.yml` is validated by `code/scripts/ocaml_toolchain_lock.py`, whose deliberately restricted YAML tokenizer skips WHOLE-LINE comments but does not strip TRAILING ones — so `uses: actions/checkout@<sha> # v7.0.1` parsed as a value ending in `# v7.0.1`, and the reviewed-action allowlist stopped matching. Two CI checks went red. The convention was also redundant there: that file's three SHAs are already bound in the script's `ACTIONS` map, so a bump cannot land without editing the contract too — a stronger review gate than a comment. The fix is a whole-line comment ABOVE each `uses:`, which the tokenizer drops and a human still reads. Generalise: before applying a repo-wide convention to a file, check whether that file has its own contract, and run that contract locally. **And grep for the path across ALL of `code/scripts/`, not just `code/scripts/tests/`, because the consumer usually names the file in a module constant the test never mentions.** That refinement is not theoretical: `grep -rl 'ci.yml' code/scripts/tests/` missed `test_elixir_windows_build_fronts.py` entirely — the test contains the string zero times, because the path lives in `WORKFLOW_PATH` inside the *validator* it imports. So the same trailing-comment convention broke a SECOND contract on the same branch, found only when CI failed a second time. `validate_elixir_windows_build_fronts.py` matches the Windows Elixir step with a regex requiring `uses: <ref>\s*\n`, and it also spans from the preceding `if:` line — so neither a trailing comment NOR a comment inserted above `uses:` works there; the note has to go above the step. The reliable search is `grep -rn '<filename>' code/scripts/ code/programs/` plus running the CI job's own command list, which is enumerable straight out of the workflow: `sed -n '<job range>p' .github/workflows/ci.yml | grep -oE 'test_[a-z0-9_]+\.py'`. Doing that surfaced all 29 metadata-contract tests at once.
