## 0. How to read this document

VOS00 promised a third proof stage: symbolic execution of each compiled kernel
entry, mitered against the model and DRAT-checked, labelled `proved` (bar
X3). It also admitted that "solver capacity at kernel-entry size is unmeasured"
(section 10.2). This document does three things.

1. It specifies the **route**: what an X3 proof is made of, as a set of
   obligations of known shapes, and how a long program is cut into pieces a SAT
   solver can swallow (sections 2 to 7).
2. It records the **capacity estimate** that decides whether the route is worth
   building (section 8), and **specifies the probe** that replaces the estimate
   with committed, reproducible numbers (section 9). The probe is the work of
   VOS-028b.
3. It states what the executor row, VOS-029, must deliver so that the route is
   designed with cut points from its first line (section 10).

The most important sentence of the document is in section 2.3: **X3 is
compositional, never one monolithic miter.** VOS00 section 10.1 drew the proof
as a single arrow from trap vector to `mret`. The calibration of section 8 shows
that a single miter over a realistic entry sits past the cliff of what the
repository's solver and proof checker can do. The route is therefore redrawn,
and VOS00 is corrected in the same PR.

Words used strictly:

* **Obligation:** one propositional formula whose UNSAT is one claim, with its
  own DRAT certificate (section 6).
* **Miter:** the formula "the two sides differ"; UNSAT means they cannot.
* **Cut point:** a place in a program where the proof stops tracking how the
  machine got there and starts again from a stated relation (section 4.2).
* **Collapsed:** a miter the AIG reduced to a trivial formula, so UNSAT proves
  nothing about the code (section 4.5).
* **Green:** within the thresholds of section 8.3.

Everything here is about the *machine* proof. X1 and X2 (host-level, by-value)
are unchanged and are VOS01's business.

### 0.1 What the numbers are and are not

| Source | Where | Status |
|---|---|---|
| Advisor calibration | section 8.2 | Measured once on a developer machine with the repository's solver crates and raised checker limits, in a scratch crate that is not committed. Not reproducible from the repository. Used to shape the design and to set provisional thresholds. |

## 1. Scope and reading guide

### 1.1 What an X3 claim is

VOS00 section 9.2 defines X3 as "proved on the image, per instance, with a
certificate". Precisely, for one kernel entry `e` (one trap vector path, one
component step reachable from the spine) in one compiled image `I` built for
one board `B` at one configuration `C` (N, P, table sizes):

> For every machine state satisfying the entry precondition, running the
> instructions of `e` in `I` under the RV32I model of `riscv-simulator` ends
> in a state `m'` with `alpha(m')` equal to the step the Warrant model
> prescribes, within the proven step bound, touching nothing outside the stated
> footprint.

Each phrase of that sentence is an obligation kind (section 3). The claim
carries every label of VOS00 section 9.3: `proved` or `bounded-proof(k=K)`,
with the instance constants and the image and board digests printed (section 5).

### 1.2 What it does not claim

VOS00 section 1.3 and section 10.3 stand. In addition:

* It proves nothing about silicon, about `rustc` (the compiler is trusted in
  the host-rustc stack, section 5.3), about trap entry and CSR side effects
  until the executor models them, or about any entry the probe did not size.
* The probe of section 9 bounds *solver capacity per obligation shape*. A green
  row says a shape of that size can be solved and certified. It does not say any
  particular kernel entry is verifiable.
* A hand-written instruction sequence is not compiler output (section 8.4).

### 1.3 Why a SAT route at all

By-value components are checked exhaustively on the host (X1). That is
enumeration over a reduced instance, 400,000 cases at most per claim (VOS01
section 5.6). It cannot reach the shipped instance (N = 64 or 256), and it checks
the Rust source as compiled for the host, not the RV32 image that boots. The
solver route answers both: a miter over *all* 2^64 masks is one formula whose
size is linear in the width, and it runs over the actual image bytes. The cost
is that it is only as good as the solver's capacity, which is the subject of
this document.

## 2. The route

### 2.1 Three stages, restated

```
   X1   by-value enumeration on the host, reduced instance, exhaustive
          what it checks: the Rust step against the Warrant model, all cases
          where it stops: the 400,000-case and 64 MiB budgets (VOS01 5.6)

   X2   X1 plus shipped-size evidence (property, fuzz) and the image-level
        refinement monitor (VOS00 10.1): boot the image, abstract at every
        trap through alpha, check against the kernel model
          label: randomized (samples traces); resource claims: example

   X3   proof on the compiled image: symbolic RV32I execution of each entry,
        cut into obligations, each bit-blasted and DRAT-checked
          label: proved, or bounded-proof(k=K)
```

X1 and X2 exist now (VOS00 section 9.2). X3 needs the executor of VOS-029.

### 2.2 Why not one big miter

A symbolic executor turns code into formulas. If you run an entry of a few
hundred instructions symbolically and also evaluate the model on the same
inputs, you get two big circuits and ask "can their outputs differ?". That is
the natural design, and it fails for a reason worth understanding.

A SAT solver does not "see" that two circuits compute the same thing; it
searches. If the two circuits are *structurally identical*, the AIG builder
hashes identical sub-expressions to the same node (VER10 section 2.2) and the
miter collapses to nothing: the solver is asked a question whose answer is
visible by inspection. If they are *structurally different* (the compiler
computed the same value another way: `x*5` as `(x<<2)+x`, a sum re-associated,
a lookup unrolled as a comparison chain), the solver must discover the
equivalence by search. For multiplication-like and addition-chain structure that
search is exponential in the number of independent pieces: about 8x per extra
32-bit term in a re-associated sum (section 8.2). A real compiled kernel is
structurally different from its model everywhere. The conclusion of the
calibration is that instruction count is not the cost; **divergence is**.

Two things make memory worse. First, the symbolic executor of `warrant-ir`
(VER19 section 3) models memory by concrete offsets only; a symbolic index into
a table becomes an if-then-else chain over every word. Second, each further
symbolic access multiplies what the solver must disentangle: the circuit grows
linearly but solving cost grows exponentially in the number of chained accesses
(section 8.2, tables D). So the route avoids symbolic offsets where it can
(concrete frame addresses, index case-splitting, section 4.3 and 4.4).

### 2.3 The route is compositional

> **Decision.** X3 is a set of small obligations tied together by a
> composition argument and a manifest. A proof is never one miter over a whole
> entry, unless the probe shows an entry is small enough to be one obligation
> with a collapse-free non-trivial certificate.

The ingredients, each specified below:

1. **Per-path splitting.** The executor enumerates paths by *concrete PC*:
   a branch whose condition is symbolic forks, and each path becomes its own
   obligation set (section 4.1).
2. **Cut points** with a **composition checker**: along a path, the proof is
   chopped into short segments; each segment is a separate miter that *assumes*
   the relation established at the previous cut and *proves* the relation at the
   next (section 4.2).
3. **Index case-splitting** where a table index is symbolic (section 4.3).
4. **Concrete frame addresses** for the stack and fixed structures
   (section 4.4).
5. **Cone-of-influence reduction**: only the state a segment reads is variable
   (section 4.4).
6. **Certified, content-addressed certificates and a composition manifest**
   (section 6).

Whether the compositional route is affordable is the open question the probe
answers (B3 and D3 in section 9). Section 8.4 states the current decision
state: the monolithic form already fails; the compositional form is pending.

### 2.4 What changes in VOS00

VOS00 section 10.1 drew X3 as "symbolic RV32 execution of each compiled kernel
entry, trap vector to mret, mitered against the bit-blasted model". Corrected in
the same PR: the proof is compositional (this section), and section 10.2's
sentence that fixed-size arrays are "within reach of inlining plus
bit-blasting" is true only for concrete or case-split indices; with symbolic
indices the calibrated limit is about two chained accesses into an eight-word
table (section 8.2). VOS00 gains a pointer to this document.

## 3. Obligation kinds

Each obligation has a formula *shape*, because the shape is what the probe
measures and what a reader needs to predict cost. Notation: `m` is machine
state (registers, `pc`, memory image), `s` the model state, `alpha` the
abstraction of VOS01 section 1.5 (ghost code in the host build; here a
bit-vector function over machine state), `inv` the invariant, `pre` the entry
precondition.

### 3.1 Path feasibility and coverage

Enumeration by concrete PC yields paths `p_1 .. p_k`, each with a path
condition `PC_i(m0)` over the initial machine state `m0`. Two facts are needed,
and the second is the one people forget:

* **Per-path soundness** (sections 3.2 to 3.4) is proved *under* `PC_i`.
* **Coverage**: `pre(m0) => PC_1 \/ ... \/ PC_k`, and the conditions are pairwise
  disjoint. Miter: `pre(m0) /\ not(OR PC_i)` is UNSAT, and for each pair
  `PC_i /\ PC_j` is UNSAT.

Why it matters: if the executor silently dropped a path (an unsupported
instruction, an exhausted fork budget), every per-path proof could pass and the
entry still be unproved. Coverage turns "the executor saw everything" from an
assumption into an obligation. A path that is infeasible (its `PC_i` is UNSAT)
is recorded as such with its certificate, never dropped.

Shape: a disjunction of path conditions, each a conjunction of branch tests over
at most a few symbolic words. Cheap in the calibration (clz-like, section 8.2
tables A) but it grows with the path count, so it is sized by the probe.

### 3.2 Per-path functional refinement

For each path `p_i` ending at `mret` (or the return instruction):

```
  pre(m0) /\ PC_i(m0) /\ m' = exec_i(m0) /\ s' = model_step(alpha(m0), in)
        /\ not( alpha(m') = s'  /\  out(m') = model_out )          is UNSAT
```

`exec_i` is the straight-line machine semantics along the path, built by the
executor. This is the heart of X3 and the obligation that explodes when
monolithic (section 2.2). With cut points it is replaced by the chained
obligations of section 4.2.

### 3.3 Closure of `inv`

The contract's invariant must hold after the step: `inv(alpha(m0)) /\ pre /\
PC_i` implies `inv(alpha(m'))`. This is the machine twin of the X1 closure
conjunct (VOS01 section 2.2). It is stated separately from refinement so a
failure points at the invariant, not the arithmetic. When `alpha(m')` equals the
model's `s'` and the model's own closure is a host-level lemma, this obligation
is a corollary, but it is cheap and is kept explicit: `inv` evaluated on
`alpha(m')`, which catches an `alpha` that is wrong in a way refinement
alone does not see.

### 3.4 Frame

Everything the entry is not allowed to change must be unchanged. For each
machine location outside the declared footprint (VOS01 section 2.7), the final
value equals the initial value. Formula shape: a conjunction of equalities over
locations, which is usually trivial because untouched memory is the same AIG
node (the structural collapse of section 4.5, *legitimate* here). The obligation
that is not trivial is the converse: that every store's *address* lies inside
the footprint. A store through a computed address is an address obligation:
`addr(store) in footprint` under `PC_i`. With a symbolic address that is a
range check over a bit-vector sum; with a concrete address it is constant-folded
and free (section 4.4).

Registers are part of the frame: callee-saved registers and `sp` must be
restored; the contract says which registers are outputs.

### 3.5 Step bound

The maximum number of RV32 instructions over all paths, as a number `K`. Two
outcomes, matching VOS00 section 9.3:

* every path is loop-free (concrete-PC enumeration terminates without unrolling):
  the bound is the maximum path length and the label is `proved`;
* a loop was unrolled to a limit: the label is `bounded-proof(k=K)` and the
  proof says so (VER20 section 4.2 is the model).

The bound is *derived from the paths*, not a separate formula, but coverage
(section 3.1) is what makes it a bound: it is a bound over *all* paths only
because the paths are all of them. The bound is then compared with the
contract's resource claim (VOS01 section 2.5).

### 3.6 Two-safety (constant-time and timing)

Where the contract carries a timing or flow label (VOS01 section 2.6), the
obligation is self-composition, as VER20 section 2: two copies of the machine,
public inputs shared, secret inputs fresh, and the observable trace (the `pc`
sequence, every load and store address and size, and the retired-instruction
count) must be equal. This is exactly the event set of VER13 section 4.3 item 4.
Miter form (VER20 section 2.3):

```
  pre(m1) /\ pre(m2) /\ public(m1) = public(m2) /\ not( trace(m1) ~ trace(m2) )
```

with `prove_with_custom_inputs` in `warrant-ir/src/ct_proof.rs:222` as the
existing pattern. Self-composition doubles the circuit, so it is probed
separately (section 9, experiments C1 and C2). It also needs a *negative*
control that must be SAT: a secret-indexed load (a table lookup on a secret).

On a concrete-PC executor the pc trace of a path is constant, so the `pc` part
of the observation is free; the address and count parts are where the work is.

### 3.7 Image checks

Two properties of the *whole image* rather than one entry. They are the
companions deferred by VOS03 (the lexical half of the shape checker, backlog
VOS-D002) and VOS02's appendix:

* **No panic path.** No reachable instruction sequence in a class K entry jumps
  to the panic handler. Checked on the compiled image by reachability over the
  decoded control-flow graph from each entry; an edge to the handler's address
  range is a finding.
* **Stack bound.** A static maximum stack depth per entry, from the frame sizes
  recorded in the image and the (acyclic) call graph SH5 guarantees.

These are graph checks, not SAT obligations, but they are certificates of the
same family: each is recorded in the manifest with its image digest and tool
version. They belong to VOS-026 and VOS-029 (the image exists then); this spec
only fixes that they are part of the X3 label (a theorem is not X3 without
them).

## 4. Decomposition rules

### 4.1 Per-path splitting

Branches in kernel entries are mostly forward and data-dependent. A symbolic
executor with *concrete PC* forks at each conditional branch whose condition
involves symbolic state and keeps the PC concrete along each fork. Why concrete
PC and not a symbolic PC with a big ite over the program counter: a symbolic PC
turns instruction fetch into a table lookup indexed by a symbolic value (the
worst case of section 2.2), and loses the natural unit of proof, the path.

Path explosion is bounded by the entry's structure (2^b paths for b independent
branches). The probe does not measure path enumeration cost (it uses a concrete
PC, forward-branch stepper); VOS-029 must report path counts per entry and fail
closed above a declared limit (section 10).

### 4.2 Cut points, and the composition argument

A *cut point* is a program location `c` (after instruction `k`) together with a
**cut relation** `R_c(m, s)` between machine state and model state. Most cuts are
the plainest relation: `s = alpha_c(m)` for the model's intermediate state at
that point, together with `pc = c` and the registers that are live.

Replace the single path obligation of section 3.2 with a chain over cuts
`c_0 < c_1 < ... < c_n`:

```
  base     :  pre(m0)                                   =>  R_{c_0}(m0, s0)
  segment j:  R_{c_{j-1}}(m, s)  /\  m' = exec_{seg j}(m)
              /\ s' = step_{seg j}(s)                   =>  R_{c_j}(m', s')
  final    :  R_{c_n}(m, s)                             =>  alpha(m) = s_final
                                                          (and sections 3.3, 3.4)
```

Each line is its own miter: the segment's *input* is a set of **fresh symbolic
variables** (the cut state is cut loose from how it was reached), constrained
by the hypothesis relation `R_{c_{j-1}}`; the formula's negated conclusion is
`not R_{c_j}`. The segment is a handful of instructions, so structure
divergence cannot accumulate: this is why 25 dependent steps went from 6.5 s to
31 ms in the calibration (section 8.2).

**What a cut buys.** The solver never has to prove that the two sides stay equal
*across* many instructions; it proves each hop, and the equalities carried
between hops are explicit.

**What the composition argument must establish.** Splitting is only sound if the
pieces really add up. A proof of the chain is an induction over `j`, and each of
the following has to be true *by construction*, not by luck, and has to be checked
by the composition checker (section 6.2):

1. **Hypothesis equals conclusion.** The hypothesis of segment `j` is, as a
   formula, *the same one* that segment `j-1` concluded (identical digest of the
   relation, identical variable mapping). If it were weaker than what was proved,
   the segment would prove its conclusion from less than we know and be sound but
   incomplete (it fails loud). If it were *stronger* than what was proved, the
   segment would assume something never established, and the chain is unsound.
   The checker rejects any hypothesis not discharged by the previous conclusion.
2. **Complete state.** The cut variables must cover everything segment `j` can
   read. A register or memory word the segment reads but the relation does not
   mention is silently treated as unconstrained fresh (sound, but possibly
   spuriously SAT) or, worse, if it is *not* made fresh and instead takes the
   value from the executor's single run, unsound for other paths. The rule:
   every location in the segment's read set is either (a) constrained by
   `R_{c_{j-1}}` or (b) declared "frame, unchanged since entry" and proved so in
   the frame obligation. The executor computes read sets; the checker verifies
   them (the cone-of-influence of section 4.4).
3. **Same model point.** `s` at the cut is the model state after exactly the
   model steps that correspond to the machine segment. The *model-step
   boundaries* are part of the cut definition and are recorded in the manifest
   (a segment that straddles an incomplete model step has no meaningful `R`).
4. **No gap or overlap.** The segments partition the path: segment `j` starts
   where `j-1` ended, covers a contiguous instruction range, the ranges
   concatenate to the whole path, and base and final obligations exist.
5. **Path condition carried.** Each segment inherits `PC_i`; a segment proved
   under a weaker condition than its path's is fine, under a stronger one it
   silently narrows coverage.

Soundness theorem of the composition (to be written and checked in the
composition checker's own tests): if the base, every segment and the final
obligation are UNSAT and conditions 1 to 5 hold, then for every initial state
satisfying `pre` and `PC_i`, the whole-path obligation of section 3.2 holds.
Proof by induction on `j`: `R_{c_j}` holds of the actual run because the actual
states satisfy the hypothesis (induction) and the segment obligation says the
hypothesis implies the conclusion.

**Where cuts go.** Per instruction is the strongest and the most obligations
(the probe's per-instruction row), per block every 8 or 32 instructions is the
trade-off between obligation count and difficulty (section 9 experiment B3
sweeps both). The right place is *source-aligned*: after each model-level
operation, because there `R` is a clean equation. That is why the owned-compile
lane (VER13 section 4.3 item 1, which emits a source map) gives cuts "by
construction" and is the fallback of section 8.5.

**A cut relation is a trusted definition.** `R` for each cut is written
(generated) by the tool; a wrong `R` that is too weak yields SAT (loud), one that
is too strong yields an unprovable *previous* segment (loud). Only the pairing
rule (condition 1) can make it silent, and that is checked. The relation family
is part of the trusted base (section 7).

### 4.3 Index case-splitting in place of arrays

Today's solver stack has no array theory (VOS00 section 10.2, section 12 row 9).
A load from `table[i]` with symbolic `i` and `T` entries becomes
`ite(i=0, w0, ite(i=1, w1, ...))`, an eq/ite chain; the AIG is linear in `T`
but the solver pays for the interaction of consecutive accesses (section 8.2
tables D). The replacement is to split the *obligation* on the index:

```
  for each v in 0..T-1:   obligation_v = obligation with  i := v  and PC /\ (i = v)
  plus one more:           PC /\ i >= T   is UNSAT or leads to the declared fault path
```

Each `obligation_v` has a *concrete* offset, which the executor handles exactly
(VER19 section 3). Total cost is the sum over `v`; worst-case is the max.
This is not free (T obligations for T entries and the product for several
independent indices), so it is sized by the probe (D3: sum and max). For
table-indexed state such as a thread table, plan for `T <= 8-16` per obligation
or one obligation per index (VOS00 section 14.3 D4, section 8.3 below).

The coverage obligation (section 3.1) must include the split: the cases
`i = 0 .. T-1` and the out-of-range case partition the precondition.

### 4.4 Concrete frame addresses and cone-of-influence

**Concrete frame addresses.** The kernel's stack and its static structures are
at link-time-known addresses (the image is hermetic, VOS22). `sp` at entry is
either a constant or a base plus a symbolic *delta that the contract bounds*.
The executor treats `sp`-relative accesses as concrete offsets into a frame
whose base is a fresh symbolic word with the alignment constraint; the loads and
stores then become plain wires, not ite chains. A store through a pointer that
is not frame- or table-relative is the address obligation of section 3.4.

**Cone of influence.** Only the variables a segment's conclusion depends on
matter; the executor drops everything else from the formula (it builds the
formula from the conclusion's cone, not from the whole machine state). This is
standard, but the *recording* is what matters here: the read set is part of the
manifest (section 6.2) because the composition argument's condition 2 is
precisely "the cone is covered by the hypothesis".

### 4.5 Legitimate structural collapse, and why a collapsed miter is not evidence

A miter whose two sides are the same AIG node reduces to the constant
"different = false". The CNF is two clauses or fewer, the solver reports UNSAT
with 0 conflicts and an empty or trivial DRAT. That is sound and uninformative.
There are two cases and they must not be confused:

* **Legitimate collapse.** The compiled code *is* the model's computation
  (a bitwise-and with the same operands; an untouched register in the frame).
  The collapse proves, correctly, that nothing differs. This is expected in the
  frame obligations and in unchanged state.
* **Vacuous collapse.** The proof is trivial because the *inputs were wrong*:
  the executor read a constant instead of a symbolic value, or the generated
  program lost entropy (every value folded to a constant, section 9.4 guard G2).
  Then UNSAT means nothing and the VER-P030 audit found exactly this failure in
  earlier miters.

The rule is to **label it, never hide it**. Every row (probe) and every
obligation (VOS-029) records the number of AND nodes in the miter's cone and a
`collapsed` flag (CNF of at most two clauses, or zero conflicts). A collapsed
*capacity* row is reported `collapsed` and never counted as a capacity datum. A
collapsed *proof* obligation is allowed only when the manifest says why
("frame: untouched") and it is not the sole certificate for the entry's
refinement. The `pick` proof of VOS-029 must carry a non-collapsed certificate
and a SAT sabotage control (section 10).

## 5. Instance labelling

Every X3 label prints, derived from the manifest and never typed by hand
(VOS00 section 9.3 rule 2):

```
  <entry> N=<..> P=<..> table=<..>  stack <owned-rv32i|host-rustc>
  image sha256:<..>  board sha256:<..>  model <riscv-simulator digest>
  paths <k> (feasible <..>, infeasible <..>)  cuts <..>  obligations <..>
  step bound <K> (proved | bounded-proof(k=K))
  largest obligation: <ands> ANDs, <conflicts> conflicts, DRAT <bytes>
  collapsed obligations: <n> (all labelled)
```

### 5.1 The X3 instance may differ from the X1 instance

X1 is enumerated at a *reduced* configuration (N = 8, VOS01 section 5.6). X3 for
a bitmap component is width-insensitive: a clz-based `pick` miter over 64 bits
solves in milliseconds (section 8.2, tables A), so the X3 instance may be the
shipped N. The label prints both: an X1 instance and an X3 instance, so nobody
reads "N = 8 exhaustive" as "N = 64 proved" or the reverse. For table-indexed
state the X3 instance is *smaller* than the shipped table unless the case-split
total is affordable (section 4.3), and the label says so.

### 5.2 Board and image digests

The image digest is the content digest of the linked image the executor read.
The board digest is the emulator board definition (VOS00 section 10.3, row 2).
Both are pinned in every certificate; a change to either invalidates the
manifest and the check fails.

### 5.3 Which stack

VER13 distinguishes two stacks for any guarantee (section 4.3 "Important
framing", section 5.2 item 6, and rule AC-7 in section 6): `host-rustc` (the
Rust as the host compiler builds it) and `owned-rv32i` (the output of the
owned compile lane). X3 on an image compiled by `rustc` is about **a binary
`rustc` produced, with `rustc` trusted**: it carries `stack = host-rustc` and
cannot retire any assumption that VER13 scopes to `owned-rv32i` (such as
`compiler.preserves_timing`). Only the owned-compile lane can print
`owned-rv32i`. The label always prints the stack.

## 6. Certificates

### 6.1 One DRAT per obligation

Each obligation is a *separate CNF* with its own DRAT proof, produced by
`cdcl-sat` with proof logging and checked by `drat-check` (VER11).
Obligations are content-addressed: the certificate id is
`sha256(DIMACS || DRAT)` and the manifest lists it.

Why separate CNFs, not one incremental solver with assumptions. UNSAT under
assumptions does *not* end in an empty clause (VER11 section 4: such proofs
"are not certificates of anything yet"). `cdcl-sat` exposes
`solve_with_assumptions` and `failed_assumptions` (`solver.rs:1077`, `:1137`)
and states that the clause of the negated failed assumptions is *implied*, but
logs no DRAT lemma for it. So an incremental run is fast for exploration (the
calibration used it) but yields no checkable proof. Two routes to certified
composition:

* **Route A, per-obligation CNFs (works today).** The hypothesis relation is
  added as clauses of the segment's own formula; each segment has a plain
  UNSAT with a plain DRAT. Costs: each segment re-pays its own cost and proofs
  are many. No solver change. This is the route VOS-029 can start on and the one
  the probe measures as "certified" (section 9, B3).
* **Route B, lemma logging in `cdcl-sat` (needs a change).** After an UNSAT
  under assumptions, emit the failed-assumption clause as a DRAT lemma, and let
  `drat-check` accept a proof that *derives a stated clause* (VER11 section 4
  promises exactly this). Then one incremental solver can serve many segments
  with one certified proof. This is logged as a discovered-work row
  (VOS-D045, with its VER-BACKLOG twin).

### 6.2 The composition manifest

A machine-readable manifest per X3 label lists, for the entry:

| Field | Meaning |
|---|---|
| `entry`, `image_sha256`, `board_sha256`, `model_digest` | what was proved, about what |
| `paths[]` | id, path-condition digest, feasible flag, instruction range |
| `obligations[]` | id, kind (section 3), path id, segment range, `cnf_sha256`, `drat_sha256`, `ands`, `collapsed`, `collapsed_reason`, conflicts, check work |
| `hypotheses` per obligation | the ids of the obligations whose conclusions it assumed, with the relation digest |
| `read_set` per obligation | the locations the segment can read (cone of influence) |
| `coverage` | the coverage obligation id for the entry, and the path list it covers |
| `step_bound` | `K` and whether `proved` or `bounded-proof(k=K)` |

The **composition checker** (a small tool, part of the trusted base) re-reads the
manifest and verifies conditions 1 to 5 of section 4.2: hypotheses are
conclusions of predecessors with equal digests; read sets are covered; model
boundaries match; segments partition the path; path conditions carry; coverage
lists every path exactly once. It re-runs `drat-check` on every certificate under
the limits below. It does not trust the executor's claim that it saw everything;
the coverage obligation is the evidence.

### 6.3 Default `drat-check` limits are a requirement

`drat-check` ships with `DEFAULT_MAX_VARS = 2^20` and `DEFAULT_MAX_WORK = 2^32`
(`drat-check/src/lib.rs:66`, `:73`). Running out only ever *rejects*. In the
calibration those defaults are exceeded by roughly 105k to 237k conflicts
(section 8.2). The temptation is to raise them until things pass. That is
forbidden here:

> The trusted kernel's limits are never raised to make a certificate pass.
> A proof the default limits reject is an obligation that is too big; the
> remedy is a better decomposition (a cut, a split), not a bigger budget. Raising
> a limit is an explicit, reviewed decision recorded in the backlog, and the
> label then prints the raised limit.

Every obligation must pass under `drat_check::Limits::default()`. The probe
reports it per row (`pass_default_limits`) and counts it in "green".

### 6.4 Replay of counterexamples

Every UNSAT obligation of a capacity or proof run has a paired SAT negative
control (section 9.4, guard G3): a one-instruction mutation whose counterexample
is *replayed* on the concrete `riscv-simulator`. That ties the bit-blasted
stepper to the simulator on every run (section 7), and proves the obligation is
not UNSAT merely because the formula is unsatisfiable for an unrelated reason.

### 8.3 Thresholds

Stated in conflicts and checker work first, seconds second (seconds depend on
the machine, conflicts do not).

An obligation is **GREEN** only if all of:

* UNSAT, with its SAT negative control passing;
* at most 100,000 conflicts and at most 10 s solve;
* DRAT at most 32 MB;
* `drat-check` accepts under the **default** `Limits` (work at most 2^32);
* peak resident memory at most 1 GB.

An entry is **feasible** when it decomposes into at most about 1,000 green
obligations totalling under 10 minutes.

Decision table:

| Outcome | Numbers | Consequence |
|---|---|---|
| Feasible as planned | A1 and A2 green at N = 32, 64; B3 green at 1000 instructions with worst step at most 10k conflicts and total at most 60 s; D2 and D3 green at T*k = 64*16; C1 green at 1000 | Fund VOS-029 with the compositional design; X3 instances may be the shipped sizes for bitmap components |
| Feasible, reduced and mitigated | B3 green only with cuts at 8 instructions or fewer, or only up to about 200 instructions; D3 green only for T at most 16; B4 only n at most 4; any required obligation exceeds the default `drat-check` limit | Fund VOS-029 with a required mitigation list (per-path splitting, cone-of-influence, cut points plus a composition checker, index case-splitting, concrete frame addresses, incremental solving with lemma logging); print reduced instance sizes on X3 labels; add an SH rule or lint keeping multi-term arithmetic out of class K code where there is no cut point |
| Infeasible: re-plan X3 | B3 worst step above 1M conflicts, or a timeout at 200 instructions with 25% divergence; D3 not green at T = 8; A1 not green at N = 32; C1 timeout at 200 | Do not fund VOS-029. Options: the owned-compile lane (VER13 section 4.3 item 1, where a source map gives cut points by construction); waiting for arrays plus equivalence sweeping (VOS00 section 12 row 9); or keeping X2 plus the monitor as the ceiling |

Why "worst step" and not only the total: a chain is only as strong as its
hardest hop, and one hop that is not green blocks the whole entry regardless of
how cheap the others are.

### 8.4 Validity limits of the calibration, and of the probe

Print these with every number, because each one limits what it supports:

1. **Hand-written code is not compiler output.** No register allocation, no
   spills, no instruction fusion, no inlining decisions. Real code may be
   easier (more shared structure) or harder (more mixing).
2. **The divergence is synthetic.** The reference side was made to differ from
   the code in controlled proportions (5%, 25%, 100% of instructions encoded
   differently). It is not the divergence a real compiler introduces.
3. **Trap entry, CSRs and `mret` are not modelled.** Only the ALU, loads and
   stores and forward branches with a concrete PC.
4. **The probe bounds solver capacity per obligation shape.** It does not prove
   any entry verifiable.
5. **One machine, one solver build.** Seconds are host-specific; the
   conflicts and work are the portable part.
6. **The advisor numbers raised the `drat-check` limits**, so every proof there
   was checkable; under the shipped limits many are not (the REJECT rows).

### 9.2 Entry points

* `check` validates a results file against the schema and the guards (section

  file; with `--check` it fails if the VOS30 spec's generated block differs.

### 9.3 BUILD

The BUILD file runs the unit tests and `run --tier quick` only. The quick tier
takes the smallest knob of each experiment, finishes in **under 30 seconds**, and
asserts **verdicts and SAT controls, never timings** (timings differ per host;
asserting them would be a flaky gate). The full tier is run by hand or nightly
and its output committed by a person reviewing it, as in the "file the probe"
rule.

### 9.4 Validity guards, on every row

These are the lessons of the VER-P030 audit and of the calibration; a row that
fails a guard is *invalid*, never a capacity datum.

**G1. Collapse accounting.** Record the number of AND nodes in the miter's cone
(`ands`) and a `collapsed` flag: the CNF has at most two clauses, or the solver
used zero conflicts. A collapsed row is reported with `result = "collapsed"` and
excluded from every threshold and table statistic. Experiment B1 (a sequence
against itself, divergence 0%) *must* report collapsed; it measures build time
and memory only.

**G2. Liveness of generated programs.** Generators keep programs live: inject a
fresh symbolic load every few instructions (default every 6), and cap the share
of entropy-killing operations (`sltu`, shifts, `and` with small constants) at a
stated fraction (default 20%). The generator computes the entropy it kept
(distinct live symbolic inputs reaching the output cone) and records it; a row
whose output cone depends on fewer than a stated number of symbolic bits
(default 8) is `collapsed`. This is the guard against the n of 200 or more rows
of table B2.

**G3. SAT negative control.** Every UNSAT experiment has a paired SAT control:
the same instance with **one mutated instruction** in the code side. The control
must be SAT, and its counterexample (a register and memory assignment) is
*replayed on the concrete `riscv-simulator`*: running the mutated sequence from
the model's assignment must produce an output that differs from the reference.
A control that is UNSAT, or whose counterexample does not replay, fails the row.
This simultaneously tests the stepper against the simulator (section 7).

**G4. Determinism.** The generator is seeded; the seed is a recorded field. A row
reproduces bit-for-bit (same DIMACS digest) from `(experiment, knob, seed)`.

### 9.5 Measurements per row, and the timeout

Per row (see the schema of section 9.6): `ands`, `vars`, `clauses`, `result`
(`unsat`, `sat`, `unknown`, `collapsed`, `refused`), `conflicts`,
`propagations`, `solve_ms` (wall), `drat_bytes`, `check_ms` (wall) and
`check_work` (the `Accepted.work` of `drat-check`), `pass_default_limits`
(checked under `Limits::default()`; the probe never raises limits, so a row too
big for the defaults records `false` and the reason), `peak_rss_kb`.

**Timeout: 120 s wall per row**, implemented as a loop over
`set_conflict_budget(Some(20_000))` with a clock check between slices
(`cdcl-sat/src/solver.rs:422`; the budget counts down per slice, so it is reset
each iteration). A timeout is `result = "unknown"` with the conflicts used so
far; **it is never dropped** (an `unknown` row is the data that says "red").
When proof logging is on and the solve times out, the DRAT bytes so far are
recorded and the check is skipped.

**Two modes for cut experiments.** Where a cut-point experiment is measured,
both are run and recorded:

* `mode = "incremental"`: one solver, assumptions per segment, no proof logging
  (fast; the form of the advisor's table B3);
* `mode = "certified"`: one fresh CNF per segment with the hypothesis as clauses,
  DRAT logged and checked under default limits (the form that would ship;
  section 6.1 route A).

The gap between them is itself a finding (the cost of certification), and the
decision uses the **certified** numbers.

* **B2 against B3** is the pair that decides the route. B2 is the cliff; B3 is

* **B4** isolates arithmetic structure (re-association, strength reduction)
  from instruction count, which is the cost driver identified in section 2.2.
* **D1, D2, D3, D4** triangulate the memory story: chained symbolic accesses
  (red), concrete offsets (the target), case-split (the substitute for arrays)
  and cut points between accesses.
* **E1** sits beside the solver rows because the X1 bar is enumeration, and
  its throughput and its refusal at N = 11 are the X1 reduced-instance
  evidence (VOS01 section 5.6). The fixture is committed so the numbers come from
  the real generated harness.

## 10. What VOS-029 must deliver

VOS-029 is the symbolic RV32I executor and the first machine proof (VER13
section 4.3 item 2). It is **designed around the compositional route**, with cut
points, per-path splitting and concretised addresses from its first line, never
added as later mitigations. It is funded only if VOS-028b's decision is one of the
first two rows of section 8.3.

1. **An RV32I symbolic executor** over `riscv-simulator::decode`, with
   concrete-PC path enumeration (section 4.1), a fork limit that fails closed,
   and a **differential against the concrete simulator** (section 7): random
   states, instruction by instruction, plus the SAT-control replay.
2. **Per-path obligations plus a coverage obligation** (section 3.1): every
   path has its refinement, closure and frame obligations, and the entry has one
   coverage obligation listing every path, feasible or not.
3. **Cut-point support with certified composition.** This needs either:
   * route A of section 6.1 (a CNF per segment with the hypotheses as clauses
     and the manifest recording them), which works today; or
   * route B: `cdcl-sat` logging the failed-assumption clause as a DRAT lemma and
     `drat-check` accepting a derived-clause proof (VOS-D045, VER-BACKLOG twin).
   Today a `solve_with_assumptions` UNSAT leaves no checkable lemma. The
   composition checker of section 6.2 is part of the deliverable.
4. **Index case-splitting** (section 4.3) and concrete frame addresses
   (section 4.4).
5. **A streaming proof sink.** `cdcl-sat` keeps the whole DRAT in memory
   (`solver.rs:375`); about 1.7 GB of resident memory per million conflicts
   makes proof memory the first resource to run out. Either the obligations stay
   under 100k conflicts (about 175 MB) or a streaming sink lands first
   (VOS-D044).
6. **`pick` proved on the compiled image at the shipped N**, with a
   **non-collapsed certificate**, a **SAT sabotage control** (a mutated image
   that must fail with a replayed counterexample) and **manifest-derived
   labels** (section 5).
7. **A re-run of probe tiers B and D on the real compiled `pick`, `insert` and
   `remove`**, replacing the proxy rows with real ones. Until then, every number in
   this document is a proxy number (the validity limits of section 8.4).

Not in VOS-029: trap-entry and CSR modelling (a later slice, with
VOS-020/VOS-021), the image checks of section 3.7 beyond `pick`'s own image,
two-safety on a real entry (VOS-026 and after), and the owned-compile lane.

## 11. Open questions and findings

### 11.1 Open questions

1. **Cut relation generation.** Cuts are easy at source-aligned points and hard
   at arbitrary instruction boundaries of compiled code. Which `rustc` output
   shapes admit a clean `R`? The probe cannot answer it (synthetic code);
   VOS-029 will, per entry.
2. **Does `alpha` itself fit a cone?** `alpha` over a 64-entry table is itself a
   circuit with table structure. The calibration did not measure the model-side
   cost separately.
3. **Memory models.** Byte-addressed loads and stores (`lbu`, `sb`) into a
   word-organized table add alignment cases the probe covers only
   lightly (D1 uses word accesses; `lbu`/`sb` appear in A and B).
4. **Incremental versus per-CNF.** If route B lands, is one incremental certified
   solver faster than many CNFs, or does the learned-clause database of an
   incremental run slow later segments? B3's two modes answer part of this.
5. **Equivalence sweeping.** VOS00 section 12 row 9 (arrays, incremental solving,
   k-induction, and the planned equivalence-sweeping work) would make the
   monolithic route cheaper. The probe's decision table keeps it as the
   `Infeasible` row's escape hatch.
6. **The owned-compile lane.** If the decision is the third row, the lane with a
   source map (VER13 section 4.3 item 1) is the way to get cuts by construction.
   Its cost (a new back end) is outside this program's current plan.

### 11.2 Findings logged in the backlog

The advisor work found six things that the VOS backlog now holds as discovered
work (VOS-D042 to VOS-D047); the ones that belong to the VER program's own
backlog are cross-referenced there.

| Finding | Row |
|---|---|
| `drat-check`'s default limits reject mid-sized proofs (2^32 work at about 105k to 237k conflicts); per-obligation budget must be set below that; raising is a reviewed decision only | VOS-D042 |
| Random straight-line programs are not a valid benchmark: they lose entropy and the miter collapses; liveness guards are mandatory | VOS-D043 (a guard of VOS-028b, section 9.4 G2) |
| Proof memory is the first resource to run out; a streaming proof sink is a likely VOS-029 prerequisite | VOS-D044 |
| `cdcl-sat` lacks certified assumption-based UNSAT (failed-assumption lemma logging) for cut-point composition | VOS-D045 |
| No `riscv32` target is installed and VOS22 does not exist, so capacity numbers are proxies until VOS-029 re-runs them | VOS-D046 |
| VOS00 section 10.2 claimed fixed-size arrays are "within reach of inlining plus bit-blasting"; true only for concrete or case-split indices | VOS-D047, done in this PR |
