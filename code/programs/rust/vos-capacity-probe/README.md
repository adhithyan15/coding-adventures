# vos-capacity-probe

The **solver and enumeration capacity probe** of the verified-OS program (VOS-028b,
[VOS30](../../../specs/VOS30-proof-route-and-capacity.md) section 9). Class P: a program, not a
library; no other crate depends on it.

## The question it answers

VOS00 promised a third proof stage: symbolic execution of each compiled kernel entry, mitered
against the model and DRAT-checked (bar X3). Whether that is buildable depends on how big an
obligation the repository's own `cdcl-sat`, `bit-blaster` and `drat-check` can swallow. The advisor
measured it once, in a scratch crate, with the checker's limits raised. This tool measures it
again, **reproducibly**, with the shipped limits, and ends by stating the VOS30 section 8.3
decision from the numbers.

```text
  experiment   what it sizes
  -----------  ------------------------------------------------------------------------------
  A1, A2       the bitmap shapes: `pick` (clz against a priority chain), insert and remove
  B1 .. B4     straight-line RV32I with synthetic divergence: the identical-sequence collapse
               (B1), the monolithic miter (B2, the cliff), the same with cut points (B3, the
               number that funds VOS-029; cuts every1/every2/every4/every8/every32), arithmetic
               with no cut point (B4)
  C1, C2       self-composition (constant time): two copies, public shared, secret fresh
  D1 .. D4     memory with no array theory: an eq/ite chain against a mux tree (D1), concrete
               offsets (D2), case-split on the index (D3), cut points between accesses (D4)
  D5           index split + cut per access + touched-word comparison, with a separate
               structural frame obligation and two-mutant G3 control (24 knobs)
  B5           SAT sweeping of B2 with the `fuse` knob; certified lemmas, G3 through the same
               sweep (24 knobs)
  E1, E2       enumeration: the generated by-value harness's throughput and refusals
```

The full plan is 445 knobs, 2,225 rows at five seeds; the quick tier is 105 rows.  B3
`every2`/`every4`, D5 and B5 are **registered** in the plan (VOS-028c3c commit A) but have **no
recorded rows yet**: the recording on CI runners follows in commit B of the same PR, and until
then `check` on the committed file refuses it for the 620 plan rows it lacks.

## What it found (VOS30 sections 8.5 and 8.6)

The committed results (2,225 rows, `code/specs/data/vos30-capacity-results.json`) are the CI
recording: run 45486250172 on GitHub `ubuntu-24.04` (64 shards, `--jobs 2`), which replaces the
earlier Mac recording of 1,625 rows. They give the section 8.3 outcome **row 1, Infeasible:
re-plan X3** (unchanged), and the section 8.6 re-plan decision **R3, compiled lane, reduced, with
cut density K = 2 and the memory shapes at their shipped T**. Certified per-instruction cuts,
`pick` and the bitmap shapes are green with a wide margin; the monolithic miter from 50
instructions, two-safety without relational cuts, and a table compared whole above 16 words are
red; B5 (equivalence sweeping) is route-green at 200 instructions with `fuse` = 2 but not at
`fuse` = 4 or at 1,000 instructions. The authoritative text is VOS30 sections 8.5 and 8.6; the
generated table in section 9.8 is the evidence, and `vos-capacity-probe decide` prints the
conditions that placed the 8.3 outcome. **Still provisional** until the named reviewer signs
(VOS-028c3d).

## How a row is made honest

Every row carries the guards of VOS30 section 9.4:

* **G1** the AND nodes in the miter's cone are *measured from the AIG*; a collapsed row (an
  identical pair of circuits, a constant fold, a propagation-only refutation) is labelled and
  excluded from every statistic. B1 *must* collapse.
* **G2** liveness is *measured on behaviour*: each declared input bit is flipped on random
  assignments (and, for a small cone, decided by a SAT query) and a row whose output cones depend
  on under half of the declared bits is collapsed.
* **G3** every UNSAT row has a paired SAT control: the same instance with one mutated instruction.
  Its model must satisfy the CNF (re-evaluated by a plain evaluator), satisfy the AIG constraints,
  and *replay*: the code side on the real `riscv-simulator`, the reference side on an independent
  concrete evaluator, and the two must differ.
* **G4** `(experiment, knob, seed)` fixes the DIMACS text bit for bit.

And the limits of section 9.5: one child process per row in its own process group, a conflict cap
with proof logging, a 120 s wall timeout per obligation (a split or chain, B3, D3 and D4, gets a
600 s row budget and records it as `wall_s`; VOS-D095), a 2 GiB resident-set cap polled every 50
ms, and the checker always run under `Limits::default()` (the probe never raises a limit).

Hardening (0.2.0, VOS-D097): the child is launched through `/bin/sh` with the fixed script
`ulimit -t "$1" || exit 126; shift; exec "$@"` as a CPU backstop (a limit that cannot be set stops the row), every variable part (the limit, the program,
the row's spec) a separate argv entry, so nothing from a results file reaches shell text; the
kill checks `/bin/kill`'s status, retries it once, falls back to `Child::kill` and waits at most 5 s; child output
is capped at 1 MiB; every file read is capped at 64 MiB; every write is atomic (temporary file in
the same directory, `create_new`, `fsync`, rename; a symlink target is refused); `--jobs` is clamped to 1..=64; and `validate`
holds every row's `(experiment, mode, knob)` to the plan's closed set, values included. The
process-group, `sh` and `ulimit` code is unix-only; the Windows BUILD runs `check` in process
and skips the sampled re-run, saying so.

## Usage

```text
vos-capacity-probe list
vos-capacity-probe run --tier quick|full [--only A1,B3] [--jobs N] --out results.json
vos-capacity-probe run --tier full --shard K/N [--run-id DIGITS --run-attempt DIGITS] [--jobs N] --out shard.json
vos-capacity-probe join --out joined.json [--expect-binary-sha256 H] [--expect-run-id I] [--expect-run-attempt A] [--expect-shards N] [--expect-jobs J] shard.json...
vos-capacity-probe sign joined.json --reviewer NAME --host LABEL --run-id I --run-attempt A --head-sha S --expect-sha256 H --verify-file verify.json --expect-verify-sha256 V --out signed.json
vos-capacity-probe check [--full] code/specs/data/vos30-capacity-results.json [--jobs N]
vos-capacity-probe check --full --shard K/N [--rerun-out F] [--run-id I --run-attempt A] code/specs/data/vos30-capacity-results.json [--jobs N]
vos-capacity-probe check --full --at-checkout [--shard K/N ...] code/specs/data/vos30-capacity-results.json [--jobs N]
vos-capacity-probe decision-diff --recorded R.json --rerun J.json [--expect-shards N]
vos-capacity-probe validate code/specs/data/vos30-capacity-results.json
vos-capacity-probe table [--check | --write]
vos-capacity-probe decide [--replan]
vos-capacity-probe merge [--add] --base A.json --fresh B.json --experiment E1 [--where field=value] [--ignore-outside] --out C.json
```

* `run --tier quick` is what BUILD runs: the smallest knob of every experiment, five seeds each,
  about ten seconds. It asserts verdicts and controls, never timings.
* `run --tier full` is the recorded offline run (hours). Its output is committed only after a named
  reviewer has regenerated it on a stated host; `dirty_tree`, `binary_sha256` and the regeneration
  banner are **self-reported**, so that review is a process control.
* `run --tier full --shard K/N` (0-based, `K < N <= 1024`; refuses `--tier quick` and `--only`) runs
  one slice of the plan: knob `i` in plan order goes to shard `i mod N`, all seeds of a knob
  together. The output carries a `recording` block (`mode`, `shard`, `jobs`, and `run_id` and
  `run_attempt` when `--run-id` and `--run-attempt` are given: explicit flags, ASCII digits, never
  read from the environment). A local run gives neither id.
* `join` turns the N shard files into one results file, or refuses with exit 2 and writes nothing:
  each input canonical and structurally valid; the shard set exactly `0..N`; the tool, binary
  digest, tree ids, revisions, host triple (not `os`), recording mode, jobs, run id and attempt
  identical; no merges or banner; each input's rows exactly the plan's shard `K/N`. The
  `--expect-*` flags refuse on a mismatch (a local run, with no run id, refuses `--expect-run-id`
  and `--expect-run-attempt`). The output has the rows in plan order and a `recording` of
  `{mode, run_id, run_attempt, shards, jobs}`; row findings print as `join: finding:` and do not
  refuse. An unknown flag is refused, so a typo cannot skip a gate. VOS30 sections 9.2 and 9.12.2.
* `check --full --shard K/N` validates the whole file, then re-runs only shard `K`'s rows (quick in
  process, full in children) with the comparison classes of VOS30 9.12.1. `--rerun-out F` writes
  those re-run rows as a canonical file with a `verify` `recording` and the verifying binary's
  `meta` (`--rerun-out` needs `--exe`, if given, to be the running binary, and is never replaced:
  it is published with a hard link); `join` fans N such files into one, and
  `decision-diff --recorded R --rerun J` (exit 2 unless `J` is a JOINED `verify` file, `R` is not a
  `verify` file, both record non-empty tree ids and have no structural finding, `J`'s
  `recording.verifies_sha256` equals the unsigned SHA-256 of `R`, and the row identities are equal;
  `--expect-shards N` pins the shard count) judges EVERY row with `results::compare_verify` (the
  one per-row rule `check --full` applies: the 9.12.1 comparison class, then the timing band where
  that class has one) and compares the section 8.3 decision, the re-plan decision and
  the cut density `K` of the two without solving: exit 1 on a difference, printed as a `row
  differences` section and a separate `decision differences` section; exit 0 only when both are
  empty. Every `check` mode first
  refuses (exit 2, nothing re-run) a structural finding, a repeated row identity, or more quick
  specs than the plan has (VOS-D134).
  Plain `check` also bounds its in-process quick re-run to 1,800 s in all, checked between rows, so the worst case is the budget plus one row's wall (VOS-D134): once spent,
  no further row starts and one finding says how many were re-run.
* `sign` writes the reviewer's `regeneration` banner (VOS-D120) into a NEW file (never in place, never
  over an existing file) and exits 2, writing nothing, unless the input is a canonical, joined,
  `record`-mode file with no banner and no merges, the run id and attempt flags equal its `recording`, `--head-sha`
  is the recorded `repo` revision and the input ids (`meta::TREE_ENTRIES`, VOS-D140) at that commit equal the recorded `trees` (VOS-D137: not ancestry, because main is squash-merged; a commit missing locally is refused with a `git fetch origin <sha>` hint), `--reviewer` and `--host` are 1 to 64
  characters of ASCII letters, digits, space and `. _ , ' @ -` (no leading, trailing or doubled
  space), the file has no structural finding, has well formed tree ids and covers the full plan,
  `--expect-sha256` (REQUIRED: the joined file's SHA-256 the join job printed) equals the
  input's digest, and the verify evidence holds (VOS-028c3c-3b-1b, VOS-D141): `--verify-file J`
  and `--expect-verify-sha256 V` are REQUIRED, `J` is the joined verify file of a `check --full
  --at-checkout` run whose bytes (read once) hash to `V`, whose `recording.verifies_sha256` is this
  file's unsigned digest, that ran at the working tree (`trees` equal, so the recorded `trees` may
  differ from it) with the recording's `shards` and `jobs`, and that is clean under
  `results::compare_verify` and `results::decision_differences` (the comparison `decision-diff`
  makes, by the same function). The banner then also records `verified` (`run_id`, `run_attempt`,
  `head_sha`, `verify_sha256`, `trees` of the verify), and the table banner names both runs. `reviewer` and `host` are self-reported and not covered by that digest: the banner
  is an unauthenticated attestation (VOS30 9.6), and the control is the human process of 9.12.2
  item 7. `table` (`--check` and `--write`) refuses, with exit 2, a results file with any structural
  finding, so a hand-edited banner never reaches the spec. The banner records that digest as `unsigned_sha256`; `validate` recomputes it from
  the file without the banner, so a row edited after signing is a structural finding. `merge` on a
  signed file clears the banner.
* `validate FILE` runs only the schema and guard rules of `check` (no re-run, no executable, no plan
  coverage, so a shard's file can be classified) and tells the findings apart: exit 2 for a
  **structural** finding or an unreadable file (the recording is discarded), exit 1 for **row**
  findings only, for example a failed control (the recording is kept and blocks the commit, VOS30
  9.12.1), exit 0 when clean.
* `check` validates every row against the schema and the guards (`tier` must be `quick` or `full`
  and the plan's for the knob; every `(experiment, mode, knob)` in the plan's closed set) and
  requires the file to hold exactly the rows of the plan: none missing, none extra, none twice, and
  every group's `seeds` equal to the seeds present (`FULL_PLAN_EXEMPT` is the reviewed list of
  rows allowed to be missing; it is empty). A file that fails any of that is refused **before
  anything is re-run**. Otherwise it **re-runs every quick-tier row** and compares the instance
  digest, the verdict, the control and the conflict count, prints a non-fatal `stale:` line for
  every recorded tree id (`trees`: the probe and its four solver crates, `git rev-parse
  HEAD:<path>`) that differs from the working tree, and runs a **seeded spot check**: full-tier
  non-E rows whose knob group the **plan** classes cheap (`cost::CHEAP`; never the recorded times; it is exactly the set `cost::derive_cheap` gives the
  committed CI recording, groups whose slowest seed is at most 3 s: 122 of 400 groups, 610 of 2,000 rows)
  are drawn in an order seeded by the SHA-256 of the results file's own bytes, each re-run in a
  child process under `run`'s limits and under what is left of a fixed 60 s budget (plus 15 s), until
  the budget is spent; expensive groups are skipped but counted; a child that does not finish is
  **not verified** and fails the check, as does verifying fewer than 16 rows (or having fewer than
  16 eligible rows: the floor is a plain constant). A re-run compares every deterministic field
  exactly (digests, size, entropy, verdict, control, conflict, propagation and proof counters,
  `cap`, `note`, the metric key set and the non-timing metric values); it compares no times. **A
  plain `check` re-solves only cheap-class rows**: the expensive ones, including groups
  `decide` reads, are verified only by `check --full`; `check` prints `decision-critical groups
  not re-solved by this run: N` (computed from what the run re-solved). It also **rebuilds, without solving, the instance of every full-tier row** it
  can (decision rows first, under their own 150 s budget: every comparable, non-plan-heavy decision row must be rebuilt or the check fails naming it; then a seeded sample, 45 s budget, in child processes; the five D3
  groups at T = 256 take about a minute each and are left to `--full`) and compares the instance
  digest, `ands`, `vars`, `clauses`, `entropy_bits` and `declared_bits`, and requires a recorded
  `collapsed` or `unsat` row to agree with the rebuilt instance's own collapse verdicts. The sample is
  deterministic, so a determined editor can grind the file to fall outside it, and an edit of only
  the timing or solver fields of an expensive row is not caught: this is **not proof**. `check`,
  `table`, `decide` and `merge` refuse a file that is not in the tool's canonical form (duplicate
  or unknown keys), and `validate` bounds every number.
* `check --full --at-checkout` (valid only with `--full`) verifies the recorded rows at the
  CHECKOUT's tree (VOS-D141): an input whose id differs from the recording prints as a
  `check: note:` line instead of a refusal, the rows are re-run with a binary built from this
  checkout under the unchanged 9.12.1 classes, and the ok line names the count and the names of the
  differing inputs. Still refused: a file with no tree ids or only the legacy whole-crate names, a
  plan-coverage gap, an unreadable checkout and an uncommitted change in an input. Green means "the
  recorded rows reproduce at this tree"; the file's own `trees` are never changed. Each
  `--rerun-out` shard records `recording.verifies_sha256`, the SHA-256 of the recorded file without
  its signing banner (the same value before and after `sign`); `join` requires it equal across
  shards. Without the flag, `check --full` is unchanged.
* `check --full` is the release gate: without `--at-checkout` it **refuses** unless every recorded tree id equals the
  working tree's (a file that records none cannot say which tree it describes), then re-runs
  every full-tier row, no sampling, each in a child (about two hours), and also requires each
  recorded solve time, check time and peak RSS to lie within a two-sided 4x band of the re-run
  and the recorded `green` to equal `green` recomputed from the re-run's measurements (in-process
  quick rows included), and the decision of the re-run rows to equal the recorded one.
* `merge` refreshes a subset of the committed rows from a fresh `run` (VOS30 section 9.2): the
  other rows stay byte-identical, a dirty fresh run or a changed row identity is refused.
  `merge --add` instead appends fresh rows whose identities are all absent from the base (a plan
  change that brings new knobs), records `"kind": "add"`, and refuses any overlap. Use `merge` 
  when `check` reports `instance_sha256 differs` on the E1 `vos-sched-fp-bitmap` rows after that
  crate's generated document changed (VOS-D103): commit, `run --tier full --only E1 --out F`,
  `merge --base R --fresh F --experiment E1 --where fixture=vos-sched-fp-bitmap --ignore-outside --out R`, then
  `table --write`.
* `table` renders the generated block of VOS30 section 9.8 (maximum over seeds, banner and the six
  validity limits first); `table --check` fails on drift, on a missing block, or on a section 8.5
  decision that the rows do not give. `decide --replan` prints section 8.6's re-plan decision (the
  row, the cut density K, the memory verdict and the conditions); `table --write` also renders those
  lines into the replan block of section 8.6, and `table --check` compares that block and 8.6's
  hand-written label (`R3, compiled lane, reduced`, `K = 2`, the memory verdict) with the rows, so
  a hand-edited label fails.
